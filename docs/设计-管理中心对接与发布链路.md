**旧 autotk 收视频链路实测结论**(本设计的关键依据):
- `HubClient.onPublishTask → runPublish`:`download`(expo-file-system 流式下载 + expo-media-library 存相册)✅ 可用;`publishVideo`(on-device 引擎)❌ 剥掉;`onStatus → reportPublishResult` ✅。

- **要剥掉**:on-device 引擎(养号/OCR/定位,D8 退役的脆弱部分)、license 激活门禁(D4)、RN 配置/监控 UI。**要留**:下载器 `downloader.ts`、`album.ts`、`publishQueue.ts`(去 publish 步)、socket 连接与保活、三项权限。

## 2. 前提(需求方已确认)

- **Hub 与手机一定同一局域网** → 视频走 `source.kind:"lan"` 直传,**不需要 Hub relay**(`relay` 字段保留但本期不启用)。
- master 与手机同 WiFi(WDA over LAN,既有前提)。
- License **不接**(D4);Hub 的 telemetry 本期不接(记账)。

## 3. 目标架构

### 3.1 三块 + 拓扑

```
┌─────────────── 内网(同一 LAN) ───────────────┐
│ 操作员桌面 apps/desktop + services/publisher      │
│   文件夹扫描 → LAN 文件服务(lan-server.ts)        │
│   → 入队 PublishTask{deviceId, source.url, caption} │
│        │ socket.io                                  │
│   services/hub ───────────────────────────────────┐ │
│        │ ①master↔Hub(flat,D3=A)                  │ │
│ GPU 主机 services/master                            │ │
│   · Hub 客户端:注册 N 台/上报状态日志/收配置/收发布 │ │
│   · ②收视频控制通道(master 侧小服务)             │ │
│   · 发布编排 + 养号 Fleet + perception 调用          │ │
│        │ ②LAN 推送「下载 url」   │ WDA(截图/操作)  │ │
│  iPhone:  收视频端(精简 autotk,后台保活)          │ │
│           + WDA + TikTok 前台                        │ │
└─────────────────────────────────────────────────────┘
   ③收视频端下载 source.url → 存相册(后台,不打断养号)
```

### 3.2 三个工作流(= 三个开发工作项)

- **W1 master↔Hub 客户端(flat)**:master 为每台手机开一个 Hub 设备身份(deviceId=UDID),照 `apps/mobile/src/hub/client.ts` 做多设备版——注册、上报 `DeviceStatus`/日志、收 `ConfigPatch` 应用到对应 PhoneSession、收 `publish:task`、回报 `publish:result`。**纯 TS 可测,不依赖 Mac。最先做。**
- **W2 收视频端(精简 autotk)**:剥成"下载+存相册"的哑代理;后台保活(location)持有到 master 的连接,收 master 下发的下载命令,存相册后回报。**壳/原生/构建需 Mac;纯逻辑(下载编排/队列)可先 TS 测。**
- **W3 master 发布编排**:收 `publish:task` → 令该机收视频端下载入相册(后台,不打断养号)→ 存好后 master 经 WDA 驱动 TikTok 走 `publish.ts` → 回报 Hub。依赖 W1+W2。

## 4. 关键决策(需审阅重点)

### D-α · master 是每台手机的唯一 Hub 设备身份
- master 注册 deviceId=UDID,承担该手机全部 Hub 交互(养号状态/日志/配置/发布)。
- **收视频端不连 Hub**(避免"一台手机两个 Hub 身份"),改连 master 的控制通道(下条)。

### D-β · 收视频端↔master 通道(✅ 已定:**β1 后台常驻**,2026-07-20)
收视频端要在**后台**收到"下载哪个视频"的指令(不打断养号),两方案:

| 方案 | 做法 | 取舍 |
|---|---|---|
| **β1 后台常驻(推荐,合你"要定位权限"的思路)** | 收视频端复用 autotk 的 socket 客户端,把连接地址从 Hub 改指 **master**(master 跑一个小 socket 服务);location 保活维持连接;master 推「download url」,端后台下载存相册、回报进度。养号**不被打断**(前台仍是 TikTok) | 需 master 跑个小服务 + 端保留 location 保活;但复用度最高、后台下载不打断养号 |
| β2 按需前台(更简、无需定位) | 发布时 master 经 WDA `activateApp` 把收视频端切前台并带上 url(deep link 或端启动即向 master 拉待办),端前台下载存相册,master 读到"完成"再切回 TikTok 发布 | 无需 master 服务、无需 location;但下载期打断该机养号,且赌 WDA 深链/切换时序 |

- **✅ 已定 β1**:与"复用 autotk + 要定位权限"的判断一致,后台下载不打断养号,吞吐更好。master 加一个小控制服务(复用 `@mc/shared` 的 publish 事件子集,端侧 `HubClient` 几乎不改、只换 URL)。
- β2 存档作备选(未来想省 master 服务/去 location 时)。

### D-γ · 发布"相册最新一条"的时序(消除竞态)
`publish.ts` 选"相册第一条(最新)"。保证正确性:**master 编排串行化**——先令收视频端下载并确认"已存相册(assetId 已知)",**再**切 TikTok 发布;期间不往该机相册写别的。可选加固:发布前用 VLM/OCR 或 assetId 兼验最新条即刚下发的视频。

### D-δ · 视频只走 LAN(同网已保证)
`PublishTask.source` 恒 `{kind:"lan", url}`;`relay` 分支本期不实现(字段保留,未来跨网再启)。

## 5. 端到端数据流(发布一条视频)

```
1. 操作员桌面:视频拖入文件夹 → scan → lan-server 注册文件得 url → 入队 PublishTask{deviceId,url,caption} → Hub
2. Hub → master(该 deviceId 的 flat 设备):publish:task
3. master:标记 publishing;经收视频通道令该机端「下载 url → 存相册」(后台)
4. 收视频端:流式下载 → createAssetAsync 存相册 → 回报 assetId/done(失败→回报 error)
5. master:确认已入相册 → runExclusive 独占该机 → WDA 切 TikTok → publish.ts(+→相册最新→下一步→文案→post→Post Now 确认)→ published/failed
6. master:publish:result(status)→ Hub → 桌面进度
```
- 失败传播沿用 `PublishStatus` 状态机(downloading/downloaded/publishing/published/failed);任一步失败即 failed,Hub 可重派。
- 养号与发布**串行不抢前台**:发布走 `PhoneHandle.runExclusive`(已实现)。
