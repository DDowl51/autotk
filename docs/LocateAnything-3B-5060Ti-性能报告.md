# LocateAnything-3B × RTX 5060 Ti 16G 性能报告(首轮实测)

> 日期:2026-07-10　脚本:`bench/locateanything/bench.py`　样本:仓库内置 `bench/locateanything/shots/`(10 张 iPhone 8 真机 TikTok 截图,750×1334)
> 定位:为「内网集中识别服务器」选型提供**实测**依据(此前只有 A100@4K 的不相干官方数)。

## TL;DR

| 指标 | 实测值 | 判定 |
|---|---|---|
| 单张中位延迟 | **477 ms@768 / 280 ms@512** | 单流(sdpa,WSL==Windows) |
| 单流吞吐 | **2.1 张/s@768 / 3.6 张/s@512** | ⚠️ **批处理不支持**(only batch=1),单卡≈单流 |
| 峰值显存 | **~8 / 16 GB** | 富余(但塞不进批,只能多实例) |
| 定位精度 | **768 全准;512 丢 shop 小✕** | 生产锁 768 |
| **单卡承载(VLM 唯一指令源)** | **裸 ~10 台 → FP8+多实例 ~35–50 台** | 几百台=多卡 |
| 单卡承载(混合兜底) | ~38 台(裸)→ ~150–200(优化) | |

**结论:模型选型通过**(精度达标),**但批处理不支持,单卡承载须下调**——「VLM 唯一指令源」单卡 ~10–50 台,几百台=多卡(详见 §7.0 实测修正)。生产须 Linux + FP8 + 一卡多实例。

## 4. 显存

- 峰值 **8.40 GB**(权重 6.8 + 激活 ~1.6 @768/batch1),16GB 卡余量 ~7.6GB。
- 估算批处理上限(768、BF16):**batch 3–4**;换 FP8 权重(~3.4GB)后 **batch 6–8**。
- ⚠️ 原生 750×1334 + dense SDPA:单个注意力算子即需 **13.9GB** → OOM。这是 Windows(无 flash-attn)的硬限制,不是模型问题。**而 768 缩放下精度已达标(§3.1),生产可直接锁定 768 输入,绕开此问题。**

## 5. 承载量换算

`可带手机数 ≈ 吞吐 × 每台调用间隔 × 0.6 余量`

### 5.1 本配置(Windows floor,2.09 张/秒)

| 每台 VLM 调用间隔 | 用法 | 可带手机数 |
|---|---|---|
| 4–5 s | 纯 VLM 每步 | **5–6 台** |
| 30 s | 混合·兜底 | **38 台** |
| 60 s | 混合·稀疏兜底 | **75 台** |

### 5.2 生产配置外推(Linux + flash-attn + 批处理 + FP8)

三层可叠加加速:批处理 batch 6–8(~3–5×)、flash-attn(省显存+提速)、Blackwell 原生 FP8(~1.5–2×)→ 合计 **~4–8×,即 8–16 张/秒**:

| 用法 | 可带手机数 |
|---|---|
| 纯 VLM 每步 | ~20–40 台 |
| **混合·兜底(推荐架构)** | **~100–290 台** ✅ |

## 6. 限制与星号(必读)

1. **本轮是「可行性 + 精度」验证,不是生产性能**。Windows + dense SDPA 是模型的最慢形态;官方 Linux only 的实质 = 显存效率依赖 flash-attn。
2. 延迟数基于 **768 缩放输入**;所幸精度在 768 下已达标,生产可沿用。
3. batch1 单流;批处理吞吐为估算,**待下一轮实测**。
4. FP8 对 grounding 坐标精度的影响未测,启用前须用 `out/boxed_*` 复核。

## 7. 「VLM = 唯一指令源」模式的承载测算(需求方 2026-07-10 定的模式)

**模式定义**:LocateAnything 是**下一步操作坐标的唯一来源**(每个动作步都调一次);OCR 只作**文本读取**工具(评论区/文案),不参与决策。即最耗 GPU 的「纯 VLM 每步」。

### 7.0 ⚠️ 实测修正(2026-07-10,WSL sdpa;推翻下方基于批处理的外推)

三条硬实测结果,**下调**承载量预期:

1. **批处理不支持**。模型自定义 generate 硬性 `only batch size = 1`。**之前「批处理带来 4–8× 吞吐」的假设作废**——vLLM/TensorRT 对此自定义架构支持也有难度。**单卡吞吐 ≈ 单流吞吐**(多台请求在一张卡上串行,并发几乎不叠加)。
2. **分辨率×精度实测**:768 → 2.10 张/秒、**全目标准**;512 → 3.57 张/秒(1.7×),但 **shop 促销的小 ✕(IMG_0002)飘 ~2% 会 miss**(该 ✕ 仅 ~15px,512 钉不准);其余目标 512 仍准。**生产锁 768 保精度**(或测 640 折中)。
3. **WSL sdpa == Windows sdpa**(均 ~477ms@768):换 OS 对 sdpa 无用,差别只在 flash-attn(25.10 glibc 太新装不上,见部署注意)。

**修正后的单卡承载(768、单实例、无批处理)**:
| 用法 | 每台间隔 | 吞吐 | 承载 |
|---|---|---|---|
| VLM 唯一指令源(现实 5s/步+8–15s 停留) | ~7–8 s | 2.1 张/s | **~9–10 台** |
| 混合兜底 | 30 s | 2.1 张/s | ~38 台 |

**没有批处理后,恢复吞吐的两条路(可叠加,G2 验证)**:
- **FP8**(Blackwell 原生)≈ 1.5–2×;
- **一卡多实例**(batch 不行就并发跑 K 个单流实例;batch1 时 GPU 未吃满、FP8 权重仅 3.4GB,一卡塞 3–4 个)≈ 2.5–3×。
- 叠加 ≈ **10–12 张/s** → VLM 唯一指令源 @7–8s **单卡 ~35–50 台**;混合 @30s **~150–200 台**。

**结论(定案方向)**:**「VLM 唯一指令源」= 单卡 ~10 台(裸)→ ~35–50 台(FP8+多实例)**,几百台必须多卡;混合模式才单卡上百。下方 §7.1–§7.2.1 的乐观外推(90–130)基于批处理假设,**已被本节推翻,仅存档**。

### 7.1 每台设备的最小调用间隔 ≈ 1.5–2 s（存档,见 §7.0 修正）

瓶颈不是 VLM,是**手机物理回路**(拿不到坐标不能下一步):

| 环节 | 耗时 | 备注 |
|---|---|---|
| 截图拉取(WDA/WiFi) | 150–250 ms | JPEG 比 PNG 省 |
| VLM 推理(感知) | 200–350 ms | 生产单次 + 高并发排队 |
| 下发动作 | 100–200 ms | WDA /actions |
| **UI 落定 settle** | **500–1000 ms** | 等新页渲染,大头 |
| **合计** | **~1–1.8 s 下限,现实 ~1.5–2.5 s** | 即便 VLM 瞬回也快不过 settle |

### 7.2 单主机承载 ≈ 20–40 台

`N ≈ GPU吞吐(张/秒) × 每台间隔(秒) × 0.65 余量`,吞吐取生产外推 12–18 张/秒:

| 配置 | 吞吐 | 间隔 | 承载 |
|---|---|---|---|
| 保守 | 12 张/s | 3 s | ~23 台 |
| 中间 | 15 张/s | 2.5 s | ~24 台 |
| 激进(压到 512) | 22 张/s | 2 s | ~29 台 |

**结论:纯 VLM 每步 ≈ 单卡 20–40 台**(激进 ~50),远低于混合模式的 100+。这是「唯一指令源」这个干净架构的成本——每步烧一次 GPU。**要几百台 = 多张卡**(如 5×5060 Ti ≈ 100–200 台),与「一卡几百台」是两个成本量级。此账须在选型时认清。

### 7.2.1 现实等待时间下的承载(生产推荐场景,需求方 2026-07-10 补充)

7.2 假设手机火力全开(间隔 1.5–2s)。**实际 TikTok 加载不快,且拟人化防风控本就需要慢**:每步可单独配等待、平均 ~5s;浏览视频停留随机 8–15s。此时每台手机**单位时间烧的 GPU 次数骤降**,承载量翻数倍。

**推荐流养号的视频周期(VLM 唯一指令源)**:

| 场景 | VLM 调用 | 周期 | 平均间隔 |
|---|---|---|---|
| 只看不互动 | 评估 1 + 划走 1 = 2 | 看 11.5s + 划 5s ≈ 16.5s | ~8.3s |
| 看 + 点赞 | 评估 + 点赞 + 划走 = 3 | 11.5s + 2×5s ≈ 21.5s | ~7.2s |

→ **每台平均 VLM 调用间隔 ≈ 6–8s**。承载(Linux+flash-attn+FP8+批处理+512,GPU 15–25 次/s):

| 配置 | GPU吞吐 | 间隔 | 承载 |
|---|---|---|---|
| 保守 | 15 次/s | 6 s | **~59 台** |
| 中间 | 20 次/s | 7 s | **~91 台** |
| 乐观 | 25 次/s | 8 s | **~130 台** |

**结论:此节奏下单卡 ~90–130 台(保守 ~60)。「VLM 唯一指令源」终于单卡上百台可行,无需退回混合模式**——因等待变长、GPU 不再是瓶颈。附带:①这些等待同时是防风控必需,与核心卖点重合,不亏;②仍受 WiFi(多 AP)与 WDA 长会话稳定性两个基础设施天花板约束,与算力无关。

### 7.2.2 盲滑优化(需求方 2026-07-10 采纳)→ 单卡 ~150 台

**决策**:「划到下一个视频」用**盲滑**——固定/标定的滑动手势(如中列 y 0.66→0.26),**不问 VLM 要坐标**。滑动手势对位置不敏感,天然安全,且**仍由划前的那次「评估」VLM 调用做危险检测(hazard gate)**——即评估确认在信息流、无弹窗后才盲滑,不牺牲安全(这正是旧 `guardBeforeSwipe` 的教训:危险检测保留,只省掉滑动坐标这一次 VLM)。

去掉每视频一次「划走」调用后,每台平均间隔从 6–8s 拉到 **~10–13s**:

| 配置 | GPU吞吐 | 间隔 | 承载 |
|---|---|---|---|
| 保守 | 15 次/s | 10 s | ~98 台 |
| 中间 | 20 次/s | 11.5 s | ~150 台 |
| 乐观 | 25 次/s | 13 s | ~211 台 |

**采纳盲滑后:单卡 ~120–180 台,目标锁 ~150。** 每视频仍保留 ≥1 次评估调用(危险检测+决策),不裸奔。

⚠️ GPU 15–25 次/s 为外推,**批处理倍数最不确定**,须 Linux 实测批处理曲线定案(§8)。

### 7.3 压缩:两个独立旋钮

- **下采样(降分辨率)= 提 VLM 速度的主杠杆**。成本 ∝ 视觉 token ∝ 像素。现已 768;768→512 像素↓~56%,延迟↓~30–45%、吞吐↑~1.4×。**有精度地板**:× 按钮在 512 下仅 ~20px,须实测 IMG_0007/0002 是否还准。
- **JPEG 编码 = 省网络,不省 VLM**。PNG→JPEG(q85)字节↓~5×、截图拉取更快、缓解 WiFi;但模型看解码后像素,不改计算量。轻微伪影,q85 一般无感。
- **两者叠加**:下采样提承载,JPEG 提网络/截图。

### 7.4 OCR/VLM 分工与 GPU 共驻

- VLM(LocateAnything):**坐标/决策**——每步 1 次。
- OCR(PaddleOCR-GPU 或 CPU):**文本读取**——仅评论/文案步,~30–80ms,负载增量小(~10–20%)。
- 显存:LA BF16 6.8GB(或 FP8 3.4GB)+ PaddleOCR ~1–2GB + 批处理激活,16GB 可容;紧张则 OCR 上 CPU。

## 8. Linux 实测——进展与修正后的下一步

> **已完成(2026-07-10,WSL sdpa)**:延迟/精度/批处理三项已测,见 §7.0。关键结论:**批处理不支持**(乘数假设作废)、512 丢小✕(锁 768)、WSL==Windows。
> **剩余待测(优先级已变)**:①**FP8**(Blackwell,~1.5–2×)②**一卡多实例吞吐**(取代批处理,~2.5–3×)③640 精度折中。flash-attn 降为可选(见 8.0)。

### 8.0 flash-attn:Ubuntu 25.10 装不上,降为可选(部署注意)

WSL 默认拉到的 **Ubuntu 25.10(resolute)整条工具链领先 CUDA 12.8**——Python 3.14、g++15、glibc 2.41 三堵墙,最后卡在 glibc 头文件与 CUDA 12.8 的 `cospi/sinpi noexcept` 冲突(需 CUDA 12.9+)。**结论:此发行版上放弃编译 flash-attn**。
- 且 flash-attn 收益有限:主要是「原生 1334 不 OOM + 略快」,而**锁 768 就不 OOM**、sdpa 与它延迟差距不大;真正瓶颈是无批处理(它也救不了)。
- **若生产要 flash-attn**:用 **Ubuntu 24.04**(glibc 2.39 + gcc13 + py3.12,匹配 CUDA 12.8,`wsl --install -d Ubuntu-24.04`),别在 25.10 死磕。sm_120 编译目标已确认在列(Blackwell 支持没问题,纯 OS 工具链问题)。

### 8.1 flash-attn 单次延迟 × 分辨率(去掉 --attn sdpa，让它走 flash-attn)

```bash
# 原生分辨率能否低显存跑（Windows 上 OOM，flash-attn 应能过）
python bench.py --model ./LocateAnything-3B --images shots --runs 5 --out out_native
# 768 / 640 / 512：三档延迟 + 精度地板（重点看 out_*/boxed_IMG_0007.PNG 的 × 准不准）
python bench.py --model ./LocateAnything-3B --images shots --runs 5 --max-side 768 --out out768
python bench.py --model ./LocateAnything-3B --images shots --runs 5 --max-side 640 --out out640
python bench.py --model ./LocateAnything-3B --images shots --runs 5 --max-side 512 --out out512
```

### 8.2 批处理吞吐曲线(定案单卡承载的关键)

```bash
# 固定分辨率（用 8.1 选定的精度地板，示例 640），扫 batch
for B in 1 2 4 8 16; do
  echo "=== batch $B ==="
  python bench.py --model ./LocateAnything-3B --images shots --max-side 640 --batch $B
done
```

每行给出 `吞吐 ≈ X 张/秒 | 峰值显存`。找**吞吐随 batch 不再上升 / 显存触顶**的拐点 = 单卡最优吞吐。
> 若报「批处理不被 generate 支持」→ 自定义模型不支持手搓 batch,改用 vLLM/TensorRT-LLM 装载后测(需该模型已被推理框架支持;未支持则单卡吞吐以 batch1×并发估算)。

### 8.3 (可选)FP8

vLLM/TensorRT-LLM 加载 FP8 权重,复核 `boxed_*` 精度(±1% 内为过)再测吞吐。Blackwell 原生 FP8 预期吞吐 ~1.5–2×、显存减半。

### 8.4 回填

把 8.1 延迟/精度地板、8.2 最优吞吐代入 §7 公式,承载量从「外推」变「定案」;回填《内网集中识别服务器-架构设计》§6 与 D1。另:直播徽标复测(修正后的 stream-video 用例)。

## 9. 暂时的结论(Linux 实测前)

- **模型选型:通过**。iPhone 8 界面上,一句文字指令即可精准定位 ×/Don't Allow/点赞键(与手工量吻合 ~1%)。
- **单卡承载(生产,VLM 唯一指令源 + 慢节奏 + 盲滑 + 压缩)**:**~120–180 台,目标锁 ~150**。保守下限 ~90。
- **几百台 = 多卡**:如需 300–450 台,约 **2–3 张 5060 Ti**(每卡 ~150),外加**多 AP WiFi** 与 **WDA 会话运维**——这两个基础设施天花板与算力无关,是几百台的真实约束。
- **最大不确定项**:批处理吞吐乘数(§8.2)。它若达 4–5×,取乐观档;若手搓 batch 不被支持、只能靠并发,取保守档 ~90。**这是唯一还需实测才能定案的数。**
