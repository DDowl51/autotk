## 0. 摘要（先读这段）

**诉求**：手机端只做「执行」（点击/滑动/截图），把「识别当前页面 → 判断任务 → 决定下一步坐标」全部移到内网一台（带 GPU 的）服务器上；一台服务器对应多台手机，规模目标「几百台」。

**结论**：**方向成立，且代码库已具备约 70%。这不是重写，是「把现有的『电脑驱动』调试模式扶正为生产形态，再从单机单台扩到单机多台」。** 而且它顺带解决了目前一直没做的 ④「后台保活」——电脑进程永不被 iOS 挂起，手机只需 WDA + TikTok 前台。

**三块现成的基础**（精确到文件）：

| 你的设想 | 现有实现 |
|---|---|
| 手机只执行 | WDA 就是手机上的执行器；电脑发 `/screenshot`、W3C `/actions`，手机不跑我们的业务逻辑 |
| 识别在电脑 | `apps/mobile/tools/ocr.ts` 已用 **tesseract.js + ImageMagick** 在电脑侧 OCR；`tools/railDetect.ts` 图像定位在电脑侧 |
| 电脑决定坐标下发手机 | `tools/wda-cli.ts` 的 `run` = `createEngine({ ui: createCalibratedUI() })`，**引擎（决策）在电脑跑，经 WDA HTTP over LAN 驱动手机**，已经是这个形态 |

**最大拦路石**：`src/wda` 目前是**全局单例**（`client.ts` 的 `baseUrl` + `session.ts` 的 `sessionId` 是模块级变量），整层假设「一进程一台手机」。**一进程管 N 台的前提，是把它重构成「每台手机一个 `WdaClient` 实例」。**

**承载量诚实话**：有 GPU 后，OCR 不再是 CPU 死穴（PaddleOCR-GPU 批处理），单机承载量能上一个量级、接近「几百台」；但真正的天花板转移到 **①WiFi/网络基础设施（几百台 iPhone 同时推截图）② WDA 会话稳定性 ③ 截图节流**。见 §6。

## 1. 背景与动机

现有两套运行拓扑（见 `apps/mobile/CLAUDE.md`「运行拓扑」）：

- **On-device**（`src/engine/onDeviceUI.ts` + RN app）：引擎跑手机上，贴近原版，但**普通 App 会被 iOS 挂起**，无人值守要做「后台保活」——**至今未做**。
- **电脑驱动**（`tools/calibratedUI.ts` + `wda-cli.ts run`）：引擎在电脑跑，手机只跑 WDA + TikTok 前台，电脑进程不挂起。**开发期一直用它做真机验证。**

用户诉求本质 = **把「电脑驱动」从「调试台/单台」升级成「生产/多台集中」**。这样：

- 手机侧极薄（只装 WDA + TikTok），装机、维护、封号替换成本都低；
- 识别集中在有 GPU 的服务器，模型可统一升级、可复用算力；
- **绕开 iOS 后台挂起**这个老大难。

## 2. 目标 / 非目标

**目标**
- 一台内网 GPU 服务器（下称「识别服务器 / RS」）并发驱动 N 台内网手机的养号/搜索/评论/主页全流程。
- 识别（OCR + 视觉定位）集中在 RS，手机零业务逻辑。
- 单机承载量做到可度量、可水平分片扩容。
- 复用现有引擎 `createEngine` 与 `TikTokUI` 接口，不改决策逻辑。

**非目标（本期不做）**
- 不重写引擎决策逻辑（概率模型、分时段调度照旧）。
- 不改 WDA × TikTok 硬约束（`snapshotMaxDepth:1`、只能截图+坐标、W3C `/actions`）。
- 不做手机端 on-device 引擎的增强（它继续作为「另一种可选形态」保留，但不再是主线）。

## 3. 现状盘点（已具备，精确到文件）

- **引擎 UI 无关**：`src/engine/index.ts` 的 `createEngine({ ui, ... })` 只依赖 `src/engine/tiktok-ui.ts` 的 `TikTokUI` 接口；换适配器即可换驱动方式。`createEngine`/`createCalibratedUI` 都是工厂，实例内部状态（`page`/`railCache`/`prof`/`size`）**已经是 per-call 闭包**，天然可多实例。
- **电脑侧识别**：
  - `tools/ocr.ts`：`recognizeBoxes()`（整屏 OCR → 归一化词框 `OcrBox`）、`readCaption()`（裁文案区→放大→阈值→OCR）。用 tesseract.js（跨 OS）。
  - `tools/railDetect.ts`：右栏白带定位点赞/评论/收藏/分享 + 红色检测关注/爱心/发送。
  - `src/vision/detect.ts`：纯 JS 像素检测（`railBandCenters`/`detectModalCard`/`detectCommentPanel`/`detectCardClose`…），**Node/RN 通用、无原生依赖**。
- **WDA over LAN**：`src/wda/*` 用 `fetch`，`setBaseUrl(WDA_URL)` 指向手机局域网 IP:8100。`resetSession()` 是「WDA 重启后自愈」开关（无人值守夜跑用）。
- **设备标定**：`tools/deviceProfile.ts` + `adaptation/devices.json`，按逻辑分辨率存锚点；`src/engine/anchors.ts` 是锚点比例单一真源。

**唯一的结构性障碍**：`src/wda/client.ts:6` 的 `let baseUrl`、`src/wda/session.ts:6` 的 `let sessionId` 是**模块级全局**——所有 `operations/*`（`screenshot`/`tap`/…）都读这两个全局。**一进程只能有一台手机的会话。**

## 4. 目标架构

```
                 ┌──────────────────────── 内网 GPU 识别服务器 (RS) ────────────────────────┐
                 │                                                                          │
                 │   ┌── 编排器 Orchestrator (Node) ──────────────┐   ┌── GPU 识别服务 ──┐   │
   管理中心 Hub ──┼──▶│  DeviceRegistry: [{udid, ip:8100, profile}] │   │  PaddleOCR-GPU   │   │
   (看板/配置/    │   │  per-device:                               │   │  批处理队列       │   │
    遥测聚合)     │   │    WdaClient(ip) ── 会话/自愈              │──▶│  截图→词框(OcrBox) │   │
                 │   │    TikTokUI 适配器 (calibratedUI 生产版)     │◀──│  返回归一化框     │   │
                 │   │    createEngine(...) 引擎实例               │   └──────────────────┘   │
                 │   │    调度器: 分时段 + 并发上限 + 背压           │   视觉像素检测(railBand   │
                 │   └────────────────────────────────────────────┘    等)留在 Node 侧(便宜)  │
                 └───────────────────────────┬──────────────────────────────────────────────┘
                                             │  WDA HTTP (LAN/WiFi)  截图↓  点击/滑动↑
        ┌───────────────┬────────────────────┼────────────────────┬───────────────┐
     iPhone#1        iPhone#2             iPhone#3     ...       iPhone#N        （每台只跑 WDA + TikTok 前台）
     WDA:8100        WDA:8100             WDA:8100               WDA:8100
```

**组件职责**
- **DeviceRegistry**：手机清单（udid、IP:8100、DeviceProfile、健康状态）。装机台可自动注册。
- **WdaClient（每台一个实例）**：封装该手机的 baseUrl + sessionId + 自愈。
- **TikTokUI 适配器（生产版 calibratedUI）**：把「视觉检测 + 坐标点击」实现出来，喂给引擎。
- **引擎实例（每台一个）**：`createEngine`，跑该手机的分时段养号。
- **调度器**：控制并发上限、错峰、背压（截图/OCR 排队时降速）。
- **GPU 识别服务**：独立进程/容器，PaddleOCR-GPU，**批处理**多台手机的截图。
- **Hub 对接**：RS 作为聚合方接入现有管理中心（看板/批量配置/遥测），Hub 不再直连手机。

## 5. 关键改动详解

### 5.1 WDA 客户端：单例 → 每设备实例（#1 拦路石）

**现状**：`request(path)` 读模块全局 `baseUrl`；`sessionPath()` 读模块全局 `sessionId`；`operations/*` 全是无参自由函数。

**目标**：把「连接 + 会话」收进一个实例。两种风格：

- **(A) `WdaClient` 类，operations 作方法**（最干净，改动最大）：
  ```ts
  class WdaClient {
    constructor(private baseUrl: string, private timeoutMs = 20000) {}
    private sessionId: string | null = null;
    request<T>(path: string, opts?: RequestInit): Promise<T> { /* 用 this.baseUrl */ }
    sessionPath(suffix: string): string { /* 用 this.sessionId */ }
    createSession(bundleId?: string): Promise<string>;
    applyFastSettings(): Promise<...>;
    resetSession(): void;
    screenshot(): Promise<string>;
    tap(p: Point): Promise<void>;
    swipe(from: Point, to: Point, dur: number): Promise<void>;
    typeText(s: string): Promise<void>;
    // …其余 operations
  }
  ```
- **(B) 自由函数接收 client 首参**（`screenshot(client)`、`tap(client, p)`）：改动小、call site 多。

**推荐 (A)**，因为 `calibratedUI`/`onDeviceUI` 里对 `screenshot/tap/swipe/typeText` 调用密集，方法式最清晰。

**兼容迁移策略（关键，降风险）**：保留一个**默认 client 单例**，让现有模块级自由函数 `screenshot()/tap()/…` **委托给默认 client**。这样：
- 现有单台 REPL、on-device RN app（`onDeviceUI`）**零改动继续跑**；
- 编排器给每台手机 `new WdaClient(ip)`，走新路径；
- 迁移可**增量**进行，不是一刀切。

**波及面**（改「源」必须同步「消费方」，遵守 CLAUDE.md 跨项目纪律）：
- `src/wda/operations/*`、`src/wda/session.ts`、`src/wda/client.ts` — 结构改。
- `tools/calibratedUI.ts` — `createCalibratedUI(log)` → `createCalibratedUI(client, log)`，内部 `screenshot()`→`client.screenshot()`。
- `tools/ocr.ts` — `recognizeBoxes()`/`readCaption()` 内部 `screenshot()` → 接收 client 或截图 buffer。
- `src/engine/onDeviceUI.ts` — 保持走默认 client（on-device 形态不变）。
- 测试：`src/wda` 无自动化测试（真机接线层），但 `calibratedUI` 的纯逻辑消费方（popup/anchors/comment 等）测试要保持绿。

### 5.2 多设备编排器（新增，`services/` 下新包）

- 每台手机一个 `{ client, ui, engine }` 三元组，`Promise` 并发跑各自的 `engine.run()`。
- **并发上限**：`min(手机数, 池上限)`，超出排队。引擎本身是 I/O 密集 + 人性化停顿（`jitter`/`sleep` 秒级），单进程 async 多路复用几百台在「并发」层面不难；难在**识别吞吐**（§6）。
- **健康与自愈**：每台独立 `resetSession()` 自愈；WDA 掉线→指数退避重连；连续失败→标记离线并告警到 Hub（复用现有 `onEvent` → stuck 告警那套）。
- **错峰**：几百台不能同一秒都截图；调度器给每台加相位偏移，平滑 GPU/网络峰值。

### 5.3 GPU 集中识别服务（新增，独立进程/容器）

- **为什么独立**：OCR 是 GPU 活，Node 不碰 GPU；拆成独立服务（PaddleOCR-GPU，HTTP/gRPC），编排器发截图、收 `OcrBox[]`。
- **批处理**：收集多台手机同一时间窗的截图，**批量喂 GPU**（GPU 吞吐靠 batch）。这是「几百台」能不能成的核心。
- **OCR 预算削减（同样重要）**：现在 `onDeviceUI`/`calibratedUI` 里 **caption/popup/comment 每步都 OCR**，几百台会把识别打爆。设计要求：
  - **按需 OCR**：只有引擎真要文本时才 OCR（提示词匹配、弹窗判定、评论解析）；纯导航步用**便宜的像素检测**（`railBandCenters` 等，留在 Node）。
  - **每视频缓存**：同一条视频的 caption/comment OCR 结果缓存到换视频（`railCache` 已有类似缓存思路，可推广）。
  - **弹窗判定分层**：先像素快筛（`detectModalCard`/白带数），命中疑似才 OCR 确认——省掉正常流每帧 OCR。
- **视觉像素检测留 Node**：`src/vision/detect.ts` 很便宜，不必上 GPU；GPU 只做 OCR（和未来可能的图像分类：直播卡/广告卡）。

### 5.4 设备注册与规模化标定

- **注册**：`services/signing-station` 已有 UDID 自动注册雏形，扩成「装机即入 DeviceRegistry（udid + 型号 + 默认 profile）」。
- **标定**：`DeviceProfile` 按逻辑分辨率存；同型号可共享一份，减少「几百台逐台标」。异形屏 `devices.json` 覆盖。`anchors.ts` 比例默认兜底。
- **IP 发现**：手机 DHCP，需固定 IP 或 mDNS/端口扫描发现 8100（`apps/desktop` 已有 Hub 端口扫描思路可借鉴）。

### 5.5 与管理中心 Hub 的边界重划

- **现状**：Hub 直连「跑 RN app 的手机」（`apps/mobile/src/hub/`）。
- **新模型**：**Hub 直连 RS（识别服务器）**，RS 聚合上报所辖 N 台手机的状态/日志、下发批量配置到对应引擎、转发发布任务。手机不再连 Hub。
- **协议复用**：`packages/shared` 的 16 事件基本够用；「设备」语义从「一部手机 = 一个 HubClient」变成「RS = 一个 HubClient，代理 N 台」。需评估是否加「聚合方/子设备」层级（**待定决策 D3**）。

### 5.6 手机侧瘦身的连带影响

手机不再跑 RN app → 原本 app 承担的三件事要迁到 RS：
- **License 激活/心跳**：现 `apps/mobile/src/license/` 按手机激活。新模型下**授权粒度**要定：按手机？按 RS？按「手机槽位」？（**待定决策 D4**）。SDK（`packages/license-sdk`）在 RS 侧调用即可。
- **遥测**：`@telemetry/sdk` 从手机侧移到 RS 侧（每台手机作为一个匿名维度）。
- **OCR 原生模块**：on-device 用 Apple Vision 原生注入；LAN 模型下由 GPU 服务替代，手机侧那份 OCR 注入**不再需要**。

## 6. 承载量与性能模型（GPU 版）

设单台手机平均每 **T** 秒产生一次「需要识别」的动作（养号人性化停顿，实测量级 T≈3~8s）。

- **网络/截图**：每张截图约 100~500KB PNG。N=300、T=5s → 均值 60 张/s、6~30MB/s。**LAN 交换机没问题，WiFi 是瓶颈**：几百台 iPhone 并发关联单个 AP 不现实，需要 ①企业级多 AP ②按 AP 分片手机 ③或 USB 有线（lightning→以太，成本高）。**这是几百台的真实天花板之一。**
- **GPU OCR**：PaddleOCR-GPU 单张整屏 ~30~80ms，**批处理**后每秒可上百张。60 张/s 在一块中端 GPU 的能力内。**配合 §5.3 的 OCR 预算削减，识别不再是瓶颈。**
- **WDA 会话**：几百个长连会话的稳定性是运维风险；需健康巡检 + 自愈 + 告警。
- **Node 事件循环**：纯 async I/O 多路复用几百路可行；CPU 侧只剩便宜的像素检测。

**结论**：有 GPU 后，**单机识别算力不再是主瓶颈**；瓶颈转移到 **WiFi 基础设施 + WDA 会话稳定性**。务实规模：**单 RS 视 WiFi 分片能力，几十~一两百台稳态**；「几百台」建议**多 RS 分片**（每 RS 带一组 AP + 一组手机），而非死磕单机。架构从第一天就按「可水平分片」设计（DeviceRegistry 按 RS 分区）。

## 7. 风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| WDA 客户端重构波及面广 | operations/calibratedUI/ocr 都要改 | 默认 client 兼容层，增量迁移；纯逻辑测试保绿 |
| WiFi 扛不住几百台 | 无线关联/带宽上限 | 多 AP 分片 + 多 RS，架构按分片设计 |
| WDA 长会话不稳 | 掉线/超时/需重启 WDA | 每台自愈 + 健康巡检 + 告警，已有 `resetSession` 基础 |
| OCR 预算失控 | 每步 OCR × 几百台 | 按需 OCR + 每视频缓存 + 像素快筛分层 |
| 识别误判放大 | 集中后错误面更大 | 复用现有「不误识别」纪律（像素快筛→OCR 确认→动作） |
| License/遥测语义变化 | 手机不再是激活主体 | 先定授权粒度（D4）再动 |

## 9. 待定决策（需求方拍板）

- **D1**：单 RS 目标承载量 —— 接受「几十~一两百台/机 + 多机分片」，还是必须「几百台/单机」（后者需极限优化+可能不现实）？
- **D2**：手机 IP 方案 —— 固定 IP / DHCP+mDNS 发现 / 端口扫描？
- **D3**：Hub 是否需要「聚合方 + 子设备」两级模型，还是 RS 直接把每台手机当独立设备上报？
- **D4**：License 授权粒度 —— 按手机 / 按 RS / 按手机槽位？（影响商业计费与 SDK 接法）
- **D5**：on-device 形态是否保留 —— 作为「不需要电脑」的轻量可选形态留着，还是彻底转 LAN-only？
