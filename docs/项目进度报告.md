## 1. 一句话状态

2.0 的纯 TypeScript 框架、TikTok 三个常驻工作流、WDA 驱动、VLM 客户端、master 多机编排、局域网自动发现、Hub/desktop 接线与发布编排已经落地并通过离线测试；当前还不能宣称生产上线，剩余关键项是真机端到端验收、WDA 长会话、receiver 多机量产接线与持久化 StateStore。

旧 `apps/mobile` 已退役，只作历史知识库；不再部署、不再标定、不再接 License/OTA。

## 2. 当前运行拓扑

```text
Ubuntu 24.04 GPU 机
└─ services/perception
   └─ LocateAnything-3B / OpenAI 兼容 HTTP :8000

Windows 控制电脑
└─ apps/desktop
   ├─ 内嵌 Hub
   ├─ 内嵌 services/master（打包为 master.cjs）
   ├─ 自动扫描各 iPhone :8100
   ├─ 后台状态与一键重启
   └─ 发布文件夹工作流

iPhone × N
├─ WDA + TikTok
└─ apps/receiver（仅发布需要）
```

默认部署由 desktop 托管 master。手动 master 只用于工程调试，两种模式不得同时运行。

## 5. 已确定的模型事实

- LocateAnything-3B 是单目标 grounding 模型；
- 不支持 batch > 1；
- 多目标由客户端在同一截图上逐个单查；
- 页级危险先做一次全屏 OCR，以 `ocr` 特征匹配；命中后才定位关闭目标；
- 直播/广告等内容标记不进入页级危险，由工作流显式判断；
- 生产默认 `max-side=640`，小目标不稳回 768；
- 当前不启用 FP8/flash-attn；
- 几百台必须按真实调用频率测算并多卡分片，不能沿用早期批处理乐观估算。

## 6. Hub 与 desktop 状态

已完成：

- master 为每台手机建立平铺 Hub 身份；
- 上报运行状态，接收参数补丁与远程暂停/恢复；
- desktop 设备页选择工作流；
- desktop 启动时自动拉起 bundled master；
- 自动发现手机并持续重扫；
- 设置页显示 master 运行、VLM、网段、扫描时间、发现/上线数、最近错误；
- 设置页支持保存并重启、一键重启与打开本地日志目录；
- 发布任务经 Hub → master → receiver → TikTok 工作流编排。

当前限制：

- master 已把工作流事件与 WDA 操作转发到 Hub/desktop 设备实时日志；该缓冲仍需真实 Electron/Hub 联调，且不是持久审计库；
- 排障的稳定证据仍以 desktop 当日文件日志和一次性 runner 产物为准；
- desktop 的最近错误是进程内状态，重启会清空，因此出错后应先留证。

## 8. 当前工程缺口

### P0：阻塞生产闭环

- **receiver 运行时配置与稳定身份**：当前 `EXPO_PUBLIC_MASTER_URL` / `EXPO_PUBLIC_UDID` 在构建期写死；同一 IPA 无法直接量产给 N 台，自动发现 `auto-<IP末段>` 也不等于真实 UDID。
- **真机端到端验证**：三个工作流和发布都还需要当前 TikTok/iOS 版本的实机结论。

### P1：上线前必须补

- **Postgres StateStore**：当前内存实现导致 DM 去重/日限额跨重启不持久。
- **失败证据增强**：一次性 runner 已有结构化产物；常驻 master 还可继续补 runId、失败自动截图与日志持久化。
- **WDA 生命周期守护**：量产时需把每台 `runwda`/tunnel/USB 会话做成明确的常驻与重启策略。

### P2：规模化

- Wi-Fi/AP 容量与客户端隔离验收；
- perception 多卡分片与背压；
- 机群真实调用频率、尾延迟与失败重试测量；
- receiver 的量产签名、安装和更新流程。
