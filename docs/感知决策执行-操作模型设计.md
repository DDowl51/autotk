# 感知-决策-执行:操作模型与主控循环设计

> 状态:**设计评审中(未动代码)** 日期:2026-07-10
> 姊妹篇:`内网集中识别服务器-架构设计.md`(管基础设施/GPU/承载量);**本篇管控制模型与操作分层**。
> 源头:需求方提出「广告目标 + 下一步目标」双识别思路与「原子操作→基本操作→动作→工作流」四层重构,本篇将其形式化。

---

## 0. 一句话

系统重构为「**主控机 = 大脑,手机 = 哑执行器**」的闭环:每步 **观测(截图+上下文)→ 决策(危险目标/期望目标)→ 执行(原子操作)→ 验证 → 再观测**。所有操作按四层组织:**原子操作 → 基本操作 → 动作 → 工作流**。

## 1. 第一性原理(公理层)

一切设计从四条不可绕开的物理事实推出:

- **A1 屏幕即真相**。`snapshotMaxDepth:1` → 读不到元素树;唯一可靠信息源 = 截图像素(+ 自己的操作历史)。任何「我以为在哪个页」的内部状态都是猜测,必须被屏幕证实。
- **A2 动作是盲的**。tap/swipe 没有返回值;效果只能由下一帧截图观测。
- **A3 环境是对抗且非确定的**。TikTok 随时可能插入:广告、弹窗、权限对话框、直播卡、内嵌网页、新版式;网络延迟使页面转换时间不定。任何动作后的结果是一个**分布**,不是确定值。
- **A4 识别有成本、有错误率**。像素检测≈免费但只认形状;OCR 便宜但只认字;VLM(LocateAnything-3B,实测 ~0.5s/次)精准但贵且偶错。

推论(全部可在现有代码里找到「补丁形态」的印证):

- **C1 唯一稳健的控制模型是闭环**(A1+A2+A3):每个可能改变屏幕的操作,**前有看、后有验**;禁止跨不确定边界的连续盲操作。
  → 过去的补丁都是它的碎片:`guardBeforeSwipe`(上划前看)、`closeCommentPanelSafely`(关后验)、文案相似度(划后验)、搜索每步 sleep 2s(粗糙的等待)。**新模型把补丁升为结构。**
- **C2 每步必须显式声明「期待什么」与「什么捣乱」**(A3):期望目标(expected)与危险目标(hazards)是每步的一等公民,不是异常处理。
- **C3 感知分层按需**(A4):像素 → OCR → VLM,谁便宜谁先;每个识别目标自己声明检测方案。
- **C4 固定 sleep 是错误原语**(A2+A3):应替换为「轮询期望目标直到出现或超时」(await)。慢网络自动多等、快网络不空耗——此前搜索流的 2s 是权宜之计,本模型将其吸收。

## 2. 每步的合同(Step Contract)——「双识别」思路的形式化

原始思路:「给一系列广告识别目标,识别到就特殊处理(找对应关闭按钮);再给一个普通的下一步识别目标,没广告或识别到下一步就执行下一步。」

形式化:每个步骤 Step 声明——

```ts
Step {
  act:      BasicOp        // 本步要做的基本操作(可为空 = 纯观察步)
  expected: Target[]       // 期望目标:证明「环境正确/可以做」的屏幕特征
  hazards:  Target[]       // 危险目标:全局集 ∪ 页面专属集(广告/弹窗/权限窗/直播卡…)
  verify:   Target[]       // 操作后的成功判据(通常 = 下一步的 expected)
  timeout:  ms             // 等待期望/验证的上限
  onFail:   Escalation     // 升级链:重试N→换位置变体→回基地→停手+告警
}
```

主控机对每步执行统一的**决策函数**:

```
loop:
  shot = screenshot(phone)
  if h = detect(hazards, shot):        # ① 危险优先(弹窗遮一切)
      execute(h.handler); continue     #    处理后重观测,本步不做
  if detect(expected, shot):           # ② 期望在 → 环境正确
      execute(act)
      await(verify, timeout)           # ③ 轮询验证(替代死 sleep)
      → 成功: 下一步 | 失败: onFail
  else:
      poll(expected, timeout)          # ④ 期望不在 ≠ 失败,先当「没加载完」等
      → 超时: onFail                   # ⑤ 升级,最后一级永远是「停手+告警」
```

要点:
- **危险优先于期望**;
- **「没识别到期望」先当加载中**,轮询吸收慢网络;
- **onFail 最后一级 = 不盲动**(只告警管理中心)——延续本项目已确立的「不乱左滑」纪律。

## 3. 目标注册表(Target)——声明式感知

一切识别对象统一为 Target,集中注册、声明式配置:

```ts
Target {
  id:      string          // ad.shop-promo / sys.location-perm / feed.live-tag / nav.search-input …
  detect:  DetectPlan[]    // 分层:[像素检测器?, OCR 词/正则?, VLM 查询语句?] 按序尝试,便宜者先
  region:  bbox?           // 归一化先验区域(缩小搜索、降误判)
  handler: Handler?        // 仅危险目标:tapTarget(某关闭钮Target) | swipeAway | deny | back | skip
  freq:    Frequency       // 检查频率(全局危险不必每帧全查,可频控)
}
```

危险目标分**三类**,处理语义不同:

| 类 | 例 | handler 语义 |
|---|---|---|
| 系统级 | 定位权限窗(sys.location-perm) | deny:WDA alert 或 OCR 点「Don't Allow/不允许」 |
| 遮挡级 | Shop 促销(ad.shop-promo)、内嵌网页(browser.inapp)、passkey | 定位**它自己声明的**关闭钮 → 点(×在哪由该 Target 说了算,不再猜右上角) |
| 分类级 | **直播卡(feed.live-tag:「直播中/LIVE」徽标)**、置顶广告评论(comment.ad-first) | **不关而是绕**:划走 / 跳过不互动 |

首批注册表(全部来自本会话真机实测,VLM 坐标已验):

- `ad.shop-promo`:OCR「choose up to…/Pick now」→ 关闭钮 VLM "the close button X below the card"(实测 (0.50,0.79),与手工量一致)
- `browser.inapp`:OCR「Scroll up for fullscreen / Sign in to continue」→ 左上×(实测 (0.07,0.75));**禁 swipe-up**
- `sys.location-perm`:WDA alert / OCR「Don't Allow/不允许」→ deny(实测命中底行按钮)
- `feed.live-tag`:OCR/VLM「直播中/LIVE」徽标(上部区域)→ swipeAway —— **stream-video.png 的正确用途即此**(bench 用例已修正)
- `comment.ad-first`:置顶蓝字 CTA → skip(沿用 isAdComment 规则)
- 期望目标例:`feed.rail`(右栏白带,像素)、`comments.panel`(面板顶边,像素)、`search.input`/`search.results`(锚点+VLM)、`publish.plus`…

## 4. 四层操作模型

```
L3 工作流 Workflow   forYou 养号 / kwSearch / persHome / publish / 分时段调度
                     = 动作序列 + 业务概率决策(chance/jitter —— 现有引擎原样保留)
L2 动作   Action     openComments / likeCurrentVideo / search(kw) / publish(v,c) …
                     = Step 序列,每步带合同(hazards/expected/act/verify/onFail)
L1 基本操作 BasicOp   locate(target) / tapTarget(t) / await(t,timeout) / check(t)
                     / handleHazards(set) / swipeNext / swipeDismiss / typeInto(t,s)
                     = 感知 + 原子;全部跑在主控机
L0 原子操作 Primitive tap(x,y) / swipe(p1,p2,dur) / typeText(s) / screenshot()
                     / activateApp(id) / alert.accept|dismiss / home()
                     = WDA 端点 1:1;手机唯一可见层;无语义、无失败判断(A2)
```

- **L0 是手机与主控的全部协议面**——手机侧零业务逻辑,天然支持「几百台哑终端」。
- **L1 是感知与动作的黏合层**:`tapTarget = locate + tap`;`await` 取代一切固定 sleep。
- **L2 的每个动作就是一张「步骤合同表」**,声明式、可单测(mock 截图序列喂决策函数)。
- **L3 不动**:现有 `createEngine` 的概率模型/分时段调度已经是纯决策层,只把 `TikTokUI` 适配器换成 L2 动作库。

例:`search(kw)` 在新模型下(对照现在的实现,所有死 sleep 消失):

| 步 | act | expected | verify | 页面专属 hazards |
|---|---|---|---|---|
| 1 | tapTarget(nav.search-icon) | feed.rail | search.input | 全局集 |
| 2 | typeInto(search.input, kw) | search.input | search.submit | 全局集 |
| 3 | tapTarget(search.submit) | — | search.results(await,替代死等10s) | 全局集 + ad.shop-promo |
| 4 | tapTarget(search.second-result) | search.results | feed.rail | 同上 |

## 5. 主控循环与上下文(整体架构落地)

> 原始诉求:「每台手机,每步操作之前,把截图和上下文传到内网主控机,主控机分析截图、结合上下文,给出下一步操作和坐标,手机执行,如此循环。」

**落地澄清(推荐 pull 模型)**:LAN 形态下手机只跑 WDA + TikTok,**没有我们的代码**——所以「手机上传截图」实为「主控经 WDA 拉截图」,「下发操作」实为「主控经 WDA 发 /actions」。循环语义与诉求完全一致,只是**主动权全在主控**,手机侧零部署、零维护(优于让手机装 agent 推截图的 push 模型;若未来 WDA 拉图成瓶颈再议 push)。

「上下文」= 主控内存中每台手机一个 PhoneSession:

```ts
PhoneSession {
  udid, ip, profile,            // 设备身份 + 标定档(iPhone 8 全场共享一份)
  cursor: { workflow, action, step },   // 工作流栈:此刻在哪个工作流哪个动作第几步
  screen: 最近 N 帧摘要,         // caption/检测结果历史 → 供时序判断(如「划没划动」)
  hazardLog: 最近处理的弹窗,     // 频控 + 防死循环(同一弹窗 3 次关不掉 → 升级告警)
  health: { wdaSession, failStreak, alert }
}
```

单步循环(每台独立并发;VLM 调用排队进 GPU 批,见姊妹篇 §5.3/§6):

```
observe:  shot = WDA.screenshot(phone)
decide:   op   = 决策函数(shot, session)     // §2;感知按 C3 分层,昂贵层按需
act:      WDA.tap/swipe/typeText(phone, op)
verify:   await(op.verify)                   // 更新 session.cursor / hazardLog
```

**冲突裁决规则(A1)**:session 说「应该在评论区」而 shot 说「在信息流」时,**以 shot 为准**,session 回写纠偏。上下文是索引,屏幕是真相。

## 6. 决策优先级(严格全序)

每帧观测后严格按序,不可交换:

1. **系统级危险**(WDA alert / 权限窗)——遮一切,最先
2. **遮挡级危险**(弹窗/广告/内嵌页)——处理后 continue 重观测
3. **分类级危险**(直播卡/广告评论)——绕行(划走/跳过)
4. **期望在** → 执行本步 act
5. **期望不在且未超时** → 轮询等待(加载中)
6. **超时** → onFail 升级:重试(≤N)→ 变体(换位置)→ 回基地 → **停手+告警**(永不盲动)

## 8. 感知预算(与承载量衔接)

对照姊妹篇 §6.2.1 实测(5060 Ti、477ms/张):

| 层 | 成本 | 使用频率 |
|---|---|---|
| 像素 | <1ms(CPU) | 每帧都可 |
| OCR | 几十 ms(GPU 批) | 每步 ≤1 次 |
| VLM | ~0.5s | 仅「危险疑似需确认」或「期望找不到需精定位」时,预算 ≈ 每台每 20–60s 一次 |

Step Contract 让 VLM 天然按需——先像素/OCR 快筛,升级才用 VLM。与「混合识别单卡 100+ 台」的承载模型自洽。
