# 远程更新方案（卖家用）

> 问题：软件交付后出 bug，能不能不收回手机、远程修好？
> 答案：**分四层，各层通道不同**。手机端 JS 热更（覆盖 ~90% 的修复）已接入**自建 OTA**
> （expo-updates + `services/update-server`），只差 Mac 出包 + 部署更新服务器。

## 更新通道总览

| 层 | 改什么会落在这层 | 通道 | 现状 |
|---|---|---|---|
| ① 服务端 | license / 装机台 / 遥测 / 更新服务器 | 卖家 VPS 上 `git pull && docker compose up -d --build` | ✅ 随时可更，买家无感 |
| ② 手机 JS | **绝大多数修复**：引擎逻辑、锚点坐标、**机型标定档 devices.json**、发布流程、UI、参数 | 自建 expo-updates OTA 热更 | 🟡 已接入 + 域名已配（autotk-ota.ddowl.tech），待 Mac 出首包 + 部署更新服务器 |
| ③ 手机原生 | 新原生模块、权限、Info.plist、升 SDK | 装机台重装（换母包→买家重开装机页覆盖安装）+ 升 runtimeVersion | ✅ 已可用，但要买家动手 |
| ④ 桌面管理中心 | 桌面端任何改动 | 手动发新 zip 给买家替换 | ⚠️ 无自动更新、也还没有安装包 |

另外一条**零发版**通道已经存在：管理中心的「批量修改设置」可以远程改所有运行参数
（概率、关键词、话术、时间段）——行为层面的调优不需要任何更新。

## ② 手机 JS 热更：自建 OTA（已接入）

**已做（代码层，本次已把域名接好）**：
- `app.json` 的 `updates` 已开：`enabled:true` + `url: https://autotk-ota.ddowl.tech/api/manifest`
  + `runtimeVersion: "1.0.0"`；`expo-updates` 已在 package.json。
- 激活地址走 `EXPO_PUBLIC_LICENSE_URL=https://license.ddowl.tech`（见 `apps/mobile/.env.example` 样板）；
  以后迁移换地址走 `src/license/override.ts` 的常量 + OTA 推送（纯 JS、runtimeVersion 不变，天然可 OTA）。
- 新服务 `services/update-server`：实现 expo-updates 协议（manifest + 资源下发 + 可选代码签名），
  9 个自动化测试验证了 manifest 格式/签名/下发/路径穿越防护。
- **代码签名是可选的**：app.json **没配** `codeSigning` 块 → 客户端不要求验签 → 服务端返回未签名
  manifest，靠 HTTPS 传输安全即可跑通。要更强再加（见「还差」第 3 条）。

**还差（只能在 Mac / VPS 做）**：
1. **部署更新服务器**到 `https://autotk-ota.ddowl.tech`：`services/update-server`（docker compose），
   `BASE_URL=https://autotk-ota.ddowl.tech`、`UPDATES_DIR` 挂卷；在 1Panel 给 `autotk-ota` 子域**建站 + HTTPS +
   反代到容器 `4200`**（同《license-1panel部署手册》的建站+反代套路）。
2. **Mac 出首个带 OTA 的 Release 包**（`expo prebuild` 会按 `updates.enabled:true` 把 expo-updates 编进包）。
   这步和其它修复的出包合并。
3. **（可选）代码签名加固**：`npx expo-updates codesigning:generate`（不是 generate-keypair；见部署清单
   4.2 完整命令）→ 证书填进 app.json 的 `codeSigning` 块、私钥给更新服务器 `CODE_SIGNING_PRIVATE_KEY`。
   不加则依赖 HTTPS，一般够用。

> ⚠️ **OTA 只对「已烤进 expo-updates 的 Release 包」生效**。装机台里现有母包没有它，
> 所以第一次交付必须是**新出的、带 OTA 的 Release 包**（反正为其它修复也得重出）。从那个包起，
> JS 层 bug 才能热更下去。
>
> ⚠️ **只有真机 Release 包能验 OTA 是否真的生效**——自动化测试只证明了服务端产出的 manifest
> 自洽，客户端能否吃下并热更要真机跑一次（发一版改动 → 手机重启 App → 看是否变成新版）。

**之后每次 JS 修复的发布动作（Mac）**：

```bash
cd apps/mobile && npx expo export --platform ios
# 目标＝更新服务器 docker compose 挂载的 data/updates（不是 /srv/.../updates，那不是容器读的目录）
ssh user@vps 'mkdir -p 〖update-server部署目录〗/data/updates/1.0.0'
scp -r dist/ user@vps:〖update-server部署目录〗/data/updates/1.0.0/$(date +%F-%H%M)/   # 丢一个新文件夹即生效
# 买家手机：下次冷启动 autotk 时自动拉取并生效，无需任何操作
```

**注意**：
- **runtimeVersion 纪律**：JS 热更只能推**同 runtimeVersion** 的包。凡改了原生（加原生模块/
  权限、升 Expo SDK）→ 必须升 `app.json` 的 runtimeVersion + 重出 Release 包 + 走装机台（③），
  否则会把不兼容的 JS 推给旧原生 → 崩溃。纯 JS 修复不用动它。
- **生效时机**：现配置是「启动检查、后台下载、下次启动生效」。autotk 常挂机多天不重启，
  故热更可能要等买家下次重开 App 才落地——不是即时。要即时可后续加「空闲时自动 reload」。

### ②-附：机型标定档（devices.json）也走这条 OTA

**结论：`apps/mobile/adaptation/devices.json` 被 Metro 内联进 JS bundle，所以「加新机型 / 改机型坐标」
就是一次普通的 ② JS 热更**——不用重装、不用换母包。买家下载后想支持一台新机型，卖家推一版 OTA 即可。

**加/改一个机型的完整动作（卖家，需要一台该机型真机）**：

```bash
# 1) 用电脑 REPL 对着该机型真机标定（TikTok 停在一条干净推荐视频页）：
cd apps/mobile
WDA_URL=http://<该机型手机IP>:8100 npm run wda:repl
#   REPL 里敲 calibrate → 检测右栏四键 + 关注红点，写进 adaptation/devices.json（键=逻辑分辨率 WxH）
#   ⚠️ 发布/导航锚点（publish*/followTab/searchIcon…）不是 calibrate 自动标的，非 iPhone8(375x667)
#      机型要按《真机操作清单》C1/C2 手工补进该机型的 "anchors"，否则该机发布/搜索会点偏。
# 2) 出 JS 包并推到更新服务器（同上面 ② 的发布动作）：
npx expo export --platform ios
scp -r dist/ user@vps:〖update-server部署目录〗/data/updates/1.0.0/$(date +%F-%H%M)/
# 3) 买家手机下次冷启动 autotk 即自动拿到新 devices.json，多这一个机型的支持
```

**⚠️ 一个必须知道的边界（本机标定优先）**：运行时的合并是「出厂 devices.json 打底，**本机标定覆盖它**」
（`realUI.ts`：`{...devices, ...stored}`）。分两种情形：
- **加一个全新机型**（买家手机从没标定过这个分辨率）→ OTA 的新档**全量生效**，无碍。这是最常见场景。
- **改一个某台手机已「标定过」的机型**（那台曾自动标定或点过「标定本机」，结果存在本机 AsyncStorage）
  → 那台**优先用自己本机的档、收不到 OTA 对该机型的坐标更新**。要它吃 OTA 版：在那台**重新点一次
  「标定本机」**（覆盖本机档），或重装 App 清掉本机缓存。

这套「本机优先」是**有意为之**——本机实测坐标通常比出厂通用值准，不该被一刀切覆盖。代价就是 OTA 改不动
已标定机型。若以后要让 OTA 能强制修正已标定机型（同时保留用户手动标定不被误抹），需要做「版本感知合并」
（给出厂档加单调 rev + 区分手动/自动标定来源）——**这是交付后的可选增强，当前不做**（改合并逻辑有迁移风险，
不值得压在交付前）。

## ③ 手机原生更新：装机台流程（已可用）

买家手机重装/升级 = 重新打开装机页，**原位覆盖安装，数据/激活都保留**。卖家侧动作：

```bash
# 1. Mac 出新的未签名母包，替换 services/signing-station/apps/autotk.ipa
# 2. ⚠️ 必须重启服务——签名缓存在内存里，不重启会继续发旧包：
cd services/signing-station && docker compose restart signing-station
# 3. 换包后体检：
pnpm --filter signing-station check
# 4. 通知买家：重新打开装机页 → 重做「登记→安装」两步（约 1 分钟/台）
```

已知短板（记录在案，交付后再补）：买家 App 内**没有「有新版」提示**，全靠卖家通知；
装机页二维码路由未实现（`qr.svg` 适配器闲置），目前二维码需卖家手动生成。

## ④ 桌面管理中心：有安装包，但更新仍需重发包

electron-builder **已接**（出 NSIS 安装包，见部署清单第 5 步 / 交付总纲六），但**无 autoUpdater**——
改了桌面端仍需重打包发新安装包给买家。交付后第一批工作建议补：electron-updater + 静态更新源，之后桌面端也能自动更新。

## 推荐的交付决策（按优先级）

1. **首个 Release 包必须带 OTA**（②，代码层已接好）——只需 Mac 上生成签名密钥 + 改 updates.url 域名，
   随其它修复一起出包。之后所有 JS 修复 = 丢一个 `expo export` 文件夹到更新服务器，不打扰买家。
2. **部署更新服务器**（`services/update-server`）——docker compose + Caddy，与其它自建后端一起上。
   可以交付后再部署（OTA 只在有「第二版」要推时才用到），但**签名密钥 + app.json 域名必须在首个包里定死**。
3. 装机台照常作为原生更新兜底（③），交付时把「升级=重开装机页」写进买家预期。
4. 桌面端明说「更新暂时由卖家发包替换」（④），别口头承诺自动更新。
