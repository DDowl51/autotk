# 远程更新方案（卖家用）

> 问题：软件交付后出 bug，能不能不收回手机、远程修好？
> 答案：**分四层，各层通道不同**。核心结论：手机端 JS 热更（覆盖 ~90% 的修复）
> **当前构建不具备**，要在下一次出包时把 expo-updates 打进去——打进去之后才有。

## 更新通道总览

| 层 | 改什么会落在这层 | 通道 | 现状 |
|---|---|---|---|
| ① 服务端 | license / 装机台 / 遥测 | 卖家 VPS 上 `git pull && docker compose up -d --build` | ✅ 随时可更，买家无感 |
| ② 手机 JS | **绝大多数修复**：引擎逻辑、锚点坐标、发布流程、UI、参数 | expo-updates（OTA 热更） | ❌ 未接入（见下） |
| ③ 手机原生 | 新原生模块、权限、Info.plist | 装机台重装（换母包→买家重开装机页覆盖安装） | ✅ 已可用，但要买家动手 |
| ④ 桌面管理中心 | 桌面端任何改动 | 手动发新 zip 给买家替换 | ⚠️ 无自动更新、也还没有安装包 |

另外一条**零发版**通道已经存在：管理中心的「批量修改设置」可以远程改所有运行参数
（概率、关键词、话术、时间段）——行为层面的调优不需要任何更新。

## ② 手机 JS 热更：现状与接入（最重要）

**现状（已核实）**：`apps/mobile` 没有 expo-updates 依赖，`ios/…/Expo.plist` 里
`EXUpdatesEnabled=false`——**已装出去的包永远不可能远程更新 JS**，这个能力必须在出包前烘进去。

**为什么值得在正式包里就带上**：这几周所有真机修复（停止守卫、发布流程、锚点、弹窗签名）
全部是 JS 层改动。带上 OTA 后，这类修复 = 卖家一条命令推送，买家手机重启 App 自动生效；
不带，则每次都要走 ③ 的「换母包 + 买家重装」。

**接入步骤（在 Mac 上、打正式包之前，约 30–60 分钟）**：

```bash
cd apps/mobile
pnpm install
npx expo install expo-updates
eas init                    # 生成 projectId（需要 Expo 账号，免费档够用）
eas update:configure        # 自动写 app.json 的 updates.url/runtimeVersion + eas.json 的 channel
# ⚠️ runtimeVersion 建议用 {"policy":"fingerprint"}——本项目有自研原生模块
#    （keepalive-native / vision-ocr），appVersion 盲策略会漏防原生不兼容。
npx expo prebuild -p ios --clean && npx pod-install ios   # 原生工程重新生成（必须）
# 然后正常出 Release 包 → 交给装机台分发
```

**之后每次 JS 修复的发布动作**：

```bash
cd apps/mobile && eas update --channel production --message "修复xxx"
# 买家手机：下次冷启动 autotk 时自动拉取并生效，无需任何操作
```

**两个决策点**：
1. **托管**：上面走 Expo 官方托管（u.expo.dev）。国内买家网络能不能稳定访问需要**实测一次**
   （装好后在买家同类网络下冷启动看能否拉到更新）；不行再切自建 expo-updates 协议服务器
   （与全自建后端姿态一致，但要多维护一个服务）。
2. **时机**：如果明天时间不够，可以先交付**不带 OTA** 的包——但要接受：第一次修 bug 时
   买家必须整包重装一次（走 ③，顺便把 OTA 烘进那个新包，之后就一劳永逸）。

## ③ 手机原生更新：装机台流程（已可用）

买家手机重装/升级 = 重新打开装机页，**原位覆盖安装，数据/激活都保留**。卖家侧动作：

```bash
# 1. Mac 出新的未签名母包，替换 services/signing-station/apps/autotk.ipa
# 2. ⚠️ 必须重启服务——签名缓存在内存里，不重启会继续发旧包：
cd services/signing-station && docker compose restart signing-station
# 3. 换包后体检：
pnpm --filter signing-station check
# 4. 通知买家：重新打开装机页 → 重做「登记→安装」两步（约 1 分钟/台）
```

已知短板（记录在案，交付后再补）：买家 App 内**没有「有新版」提示**，全靠卖家通知；
装机页二维码路由未实现（`qr.svg` 适配器闲置），目前二维码需卖家手动生成。

## ④ 桌面管理中心：暂时只能手动

无 electron-builder（连安装包都没有）、无 autoUpdater。近期现实做法：
发新 zip → 买家解压替换 → 重开。交付后第一批工作里建议补：electron-builder 打安装包
→ 加 electron-updater + 一个静态更新源，之后桌面端也能自动更新。

## 推荐的交付决策（按优先级）

1. **明天出包前把 expo-updates 烘进去**（②）——一次 30–60 分钟的投入，换来以后所有
   JS 修复不打扰买家。这是本方案里杠杆最大的一件事。
2. 装机台照常作为原生更新兜底（③），交付时把「升级=重开装机页」写进买家预期。
3. 桌面端明说「更新暂时由卖家发包替换」（④），别口头承诺自动更新。
