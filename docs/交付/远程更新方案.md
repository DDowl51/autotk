# 远程更新方案（卖家用）

> 问题：软件交付后出 bug，能不能不收回手机、远程修好？
> 答案：**分四层，各层通道不同**。手机端 JS 热更（覆盖 ~90% 的修复）已接入**自建 OTA**
> （expo-updates + `services/update-server`），只差 Mac 出包 + 部署更新服务器。

## 更新通道总览

| 层 | 改什么会落在这层 | 通道 | 现状 |
|---|---|---|---|
| ① 服务端 | license / 装机台 / 遥测 / 更新服务器 | 卖家 VPS 上 `git pull && docker compose up -d --build` | ✅ 随时可更，买家无感 |
| ② 手机 JS | **绝大多数修复**：引擎逻辑、锚点坐标、发布流程、UI、参数 | 自建 expo-updates OTA 热更 | 🟡 已接入（客户端配置 + 服务端已就绪），待首个 Release 包 + 部署更新服务器 |
| ③ 手机原生 | 新原生模块、权限、Info.plist、升 SDK | 装机台重装（换母包→买家重开装机页覆盖安装）+ 升 runtimeVersion | ✅ 已可用，但要买家动手 |
| ④ 桌面管理中心 | 桌面端任何改动 | 手动发新 zip 给买家替换 | ⚠️ 无自动更新、也还没有安装包 |

另外一条**零发版**通道已经存在：管理中心的「批量修改设置」可以远程改所有运行参数
（概率、关键词、话术、时间段）——行为层面的调优不需要任何更新。

## ② 手机 JS 热更：自建 OTA（已接入）

**已做（代码层）**：
- `apps/mobile/package.json` 加了 `expo-updates`；`app.json` 配好 `updates`（指向自建
  `https://updates.你的域名.com/api/manifest`）+ `runtimeVersion: "1.0.0"` + 代码签名。
- 新服务 `services/update-server`：实现 expo-updates 协议（manifest + 资源下发 + 代码签名），
  9 个自动化测试验证了 manifest 格式/签名/下发/路径穿越防护。
- `EXUpdatesEnabled` 会在 Mac `expo prebuild` 时由 app.json 的 `updates.enabled:true` 翻成 true。

**还差（只能在 Mac / VPS 做）**：
1. **生成代码签名密钥对**（Mac，首次 prebuild 前）：见 `apps/mobile/code-signing/README.md`——
   `npx expo-updates codesigning:generate`（不是 generate-keypair；见部署清单 4.2 的完整命令），证书留 App、私钥给更新服务器。
2. **把 app.json 的 `updates.url` 改成你的真实域名**，再出 Release 包（这一步和其它修复的出包合并）。
3. **部署更新服务器**：`services/update-server`（docker compose + Caddy，见其 README），
   `BASE_URL` 与 app.json 同域、私钥就位。

> ⚠️ **OTA 只对「已烤进 expo-updates 的 Release 包」生效**。装机台里现有母包没有它，
> 所以第一次交付必须是**新出的、带 OTA 的 Release 包**（反正为其它修复也得重出）。从那个包起，
> JS 层 bug 才能热更下去。
>
> ⚠️ **只有真机 Release 包能验 OTA 是否真的生效**——自动化测试只证明了服务端产出的 manifest
> 自洽，客户端能否吃下并热更要真机跑一次（发一版改动 → 手机重启 App → 看是否变成新版）。

**之后每次 JS 修复的发布动作（Mac）**：

```bash
cd apps/mobile && npx expo export --platform ios
# 目标＝更新服务器 docker compose 挂载的 data/updates（不是 /srv/.../updates，那不是容器读的目录）
ssh user@vps 'mkdir -p 〖update-server部署目录〗/data/updates/1.0.0'
scp -r dist/ user@vps:〖update-server部署目录〗/data/updates/1.0.0/$(date +%F-%H%M)/   # 丢一个新文件夹即生效
# 买家手机：下次冷启动 autotk 时自动拉取并生效，无需任何操作
```

**注意**：
- **runtimeVersion 纪律**：JS 热更只能推**同 runtimeVersion** 的包。凡改了原生（加原生模块/
  权限、升 Expo SDK）→ 必须升 `app.json` 的 runtimeVersion + 重出 Release 包 + 走装机台（③），
  否则会把不兼容的 JS 推给旧原生 → 崩溃。纯 JS 修复不用动它。
- **生效时机**：现配置是「启动检查、后台下载、下次启动生效」。autotk 常挂机多天不重启，
  故热更可能要等买家下次重开 App 才落地——不是即时。要即时可后续加「空闲时自动 reload」。

## ③ 手机原生更新：装机台流程（已可用）

买家手机重装/升级 = 重新打开装机页，**原位覆盖安装，数据/激活都保留**。卖家侧动作：

```bash
# 1. Mac 出新的未签名母包，替换 services/signing-station/apps/autotk.ipa
# 2. ⚠️ 必须重启服务——签名缓存在内存里，不重启会继续发旧包：
cd services/signing-station && docker compose restart signing-station
# 3. 换包后体检：
pnpm --filter signing-station check
# 4. 通知买家：重新打开装机页 → 重做「登记→安装」两步（约 1 分钟/台）
```

已知短板（记录在案，交付后再补）：买家 App 内**没有「有新版」提示**，全靠卖家通知；
装机页二维码路由未实现（`qr.svg` 适配器闲置），目前二维码需卖家手动生成。

## ④ 桌面管理中心：有安装包，但更新仍需重发包

electron-builder **已接**（出 NSIS 安装包，见部署清单第 5 步 / 交付总纲六），但**无 autoUpdater**——
改了桌面端仍需重打包发新安装包给买家。交付后第一批工作建议补：electron-updater + 静态更新源，之后桌面端也能自动更新。

## 推荐的交付决策（按优先级）

1. **首个 Release 包必须带 OTA**（②，代码层已接好）——只需 Mac 上生成签名密钥 + 改 updates.url 域名，
   随其它修复一起出包。之后所有 JS 修复 = 丢一个 `expo export` 文件夹到更新服务器，不打扰买家。
2. **部署更新服务器**（`services/update-server`）——docker compose + Caddy，与其它自建后端一起上。
   可以交付后再部署（OTA 只在有「第二版」要推时才用到），但**签名密钥 + app.json 域名必须在首个包里定死**。
3. 装机台照常作为原生更新兜底（③），交付时把「升级=重开装机页」写进买家预期。
4. 桌面端明说「更新暂时由卖家发包替换」（④），别口头承诺自动更新。
