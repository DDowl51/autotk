## 0. 摘要(一页看懂)

**在做什么**:把 autotk(WDA 驱动 iPhone 上 TikTok 的自动化系统)从「引擎跑在手机上、逐机标定、on-device 识别」**推倒重来**,重构为「**内网 Linux GPU 主机是大脑,手机是哑执行器,GPU 视觉模型(LocateAnything-3B)是下一步操作坐标的唯一来源**」的集中式闭环系统。需求方已拍板:全新实现、不复用旧代码(旧代码仅作知识库)、严格第一性原理。

**当前阶段**:两条线并行——① **架构设计**(已产出总纲 + 分册 + G0 规格,基本成型);② **模型选型实测**(LocateAnything-3B 在目标 GPU RTX 5060 Ti 上跑通,精度达标,但性能实测**推翻了早期乐观外推**)。

**最关键的三个结论(实测)**:
1. **模型选型通过**:LocateAnything-3B 用一句文字指令即可精准定位 ×/Don't Allow/点赞键等目标,与手工标定坐标吻合 ~1%,正是所需。
2. **承载量须大幅下调**:模型**不支持批处理**(only batch=1),**FP8/flash-attn 在当前 Blackwell 软件栈上都跑不起来**(生态太新、预编译 kernel 不匹配)。单卡单流吞吐仅 **2.1 张/秒@768**。「VLM 唯一指令源」模式下**单卡 ~10 台**(裸),几百台 = 多卡。
3. **硬件天花板转移**:算力之外,几百台的真实约束是 **WiFi 基础设施**与 **WDA 长会话稳定性**。

## 1. 项目背景与本阶段目标

- **产品**:autotk = TikTok 养号/营销互动自动化。旧系统引擎跑手机端(RN/Expo),受 iOS 后台挂起限制、需逐机坐标标定、on-device OCR/像素识别。
- **重构动因**:需求方要「一台内网电脑管几百台手机、识别集中在电脑端、手机只执行」。这恰好也解决旧系统未做的「后台保活」难题(电脑进程不挂起)。
- **本阶段目标**:① 定架构;② 选定并验证集中识别的核心——GPU 视觉模型;③ 摸清单卡承载量,给采购/部署提供实测依据。

## 2. 架构决策

### 2.1 第一性原理(四公理)
- **A1 屏幕即唯一真相**:WDA `snapshotMaxDepth:1` 约束下读不到元素树,唯一可靠信息 = 截图像素。
- **A2 动作是盲的**:tap/swipe 无返回值,效果只能由下一帧截图观测。
- **A3 环境对抗且非确定**:TikTok 随时插广告/弹窗/权限窗/直播卡/内嵌网页;网络使页面转换时间不定。
- **A4 识别有成本、有错误率、是稀缺资源**:像素≈免费、OCR 便宜、VLM 精准但贵(~0.5s/次)且是吞吐瓶颈。

### 2.2 由公理推出的核心决策
- **闭环控制**:每个改变屏幕的操作前有观测、后有验证。
- **每步显式声明 expected(期望)与 hazards(危险)**——「双识别」思路的形式化(Step 合同)。
- **VLM 是坐标/决策唯一来源**;OCR 只读文本(评论/文案);**盲滑是唯一例外**(固定手势,但前置危险检测)。
- **固定 sleep → `await(target, timeout)` 轮询**。
- **手机零业务逻辑**:只跑 WDA + TikTok,全部智能在主控(pull 模型:主控经 WDA 拉截图、下发动作)。
- **onFail 最后一级永远是「停手+告警」**,绝不盲动脱困(旧系统血泪)。
- **系统弹窗不走 WDA /alert**:统一截图 + VLM 定位 + tap(带地图的定位窗 /alert 读不到,已实证)。

### 2.3 四层操作模型
```
L3 工作流   业务概率决策(chance/jitter/分时段/占比)——纯逻辑
L2 动作     Step[] 序列,每步带合同(hazards/expected/act/verify/onFail)
L1 基本操作 locate/tapTarget/await/handleHazards/swipeNext(盲滑)/typeInto/readText
L0 原子     tap/swipe/typeText/screenshot/activateApp/pressHome —— WDA 端点 1:1,手机唯一可见层
```

### 2.4 系统拓扑
```
Linux GPU 主机: services/master(Node/TS 主控编排) ──HTTP──> services/perception(Python: LocateAnything + OCR + 批处理)
   │ 接管理中心(复用现有 services/hub, 聚合上报 N 台)
   │ WDA HTTP over LAN/WiFi(截图↓ / 原子操作↑)
   └── iPhone8 #1..#N(只跑 WDA + TikTok 前台, 零我方代码)
```

## 4. LocateAnything-3B 模型评估

### 4.1 模型能力
- NVIDIA 2026-05 开源的**视觉定位(grounding)模型**:给「截图 + 文字指令」,直接返回边界框/点坐标。
- 覆盖:GUI 元素定位、OCR 文字定位、开放目标检测、点选、指代表达。
- 架构:Qwen2.5-3B-Instruct + MoonViT-SO-400M 视觉编码器,3B 参数,BF16 权重 ~6.8GB。
- 核心加速 **Parallel Box Decoding(PBD)**:框坐标一步并行出,不走自回归。
- 支持到 2.5K 分辨率、支持 Blackwell 架构;**官方标注 Linux only、推荐 BF16**。
- **对本项目的意义**:一个模型即可替掉旧系统的 tesseract OCR + 像素启发式两套定位,且直接给出弹窗 ×/Don't Allow/点赞键的坐标——正是「VLM 唯一指令源」所需。

### 4.2 环境搭建历程(踩坑全记录,供部署参考)

目标 GPU:**RTX 5060 Ti 16GB(Blackwell, sm_120)**。历经 Windows 原生 → WSL2 的迁移,连撞多堵「生态太新」的墙:

| 环节 | 问题 | 解法/结论 |
|---|---|---|
| PyTorch 认卡 | 默认 torch 不支持 sm_120 | 必须 **cu128 轮子**(`--index-url .../whl/cu128`);capability 应为 (12,0) |
| 模型下载 | huggingface.co 被墙(SSLEOFError) | 用镜像 `HF_ENDPOINT=https://hf-mirror.com` 或代理;须同窗口设 + echo 验证 |
| 依赖缺失 | 缺 decord/lmdb/torchvision | 补装;torchvision 须走 cu128 源配套 |
| 版本冲突 | huggingface_hub 1.x 与 transformers 4.57.1 冲突 | 钉 `huggingface_hub<1.0` |
| 模型 API | generate 需 image_grid_hws / use_cache=True;返回可能是元组 | 按官方完整示例调用 |
| 显存 OOM | 原生 1334 分辨率 dense SDPA 单个注意力算子需 13.9GB | **下采样到 768**(`--max-side 768`);且 ground 须 `@torch.no_grad()` |
| Python 版本 | WSL 默认给了 **Python 3.14**,轮子普遍缺 | 重建 venv 用 **3.11** |
| flash-attn | Ubuntu 25.10(resolute)整条链太新:py3.14 / g++15 / **glibc 2.41 与 CUDA 12.8 头文件冲突**(cospi/sinpi noexcept) | **放弃**(sm_120 编译目标已在列,纯 OS 工具链问题);生产要它用 **Ubuntu 24.04** |
| FP8(torchao) | kernel 版本矩阵死循环(见 §4.3) | **放弃**(当前 Blackwell FP8 生态未成熟) |
| 批处理 | 模型硬性 `only batch size = 1` | **不支持**(vLLM/TRT 对此自定义架构支持也难) |

**最终可用环境**:WSL2 Ubuntu 25.10 + Python 3.11 + **torch 2.8.0+cu128** + transformers 4.57.1 + BF16 + dense SDPA + 下采样 768。

### 4.3 性能实测(全部数据)

测试样本:仓库内 10 张 iPhone 8(750×1334)真机 TikTok 截图,覆盖点赞键/×/Don't Allow/文案/评论/搜索页。每张多次取中位。

**延迟 × 配置**:
| 配置 | 单张中位延迟 | 单流吞吐 | 峰值显存 | 备注 |
|---|---|---|---|---|
| BF16 768(Windows) | 477.7 ms | 2.09 张/s | 8.40 GB | 首轮基线 |
| BF16 768(WSL) | 477.2 ms | 2.10 张/s | 8.27 GB | **WSL == Windows**,换 OS 对 sdpa 无用 |
| BF16 512(WSL) | 279.9 ms | 3.57 张/s | 7.98 GB | 快 1.7×,但**精度掉**(见下) |
| FP8 torch2.11(torchao) | 1152 ms | 0.87 张/s | 8.32 GB | kernel 为 sm_90a/py310 编,加载失败→慢速回退 |
| FP8 torch2.8(torchao) | 661 ms | 1.51 张/s | 5.50 GB | torchao 要 torch≥2.11,cpp 扩展被跳过→慢 |
| **多实例 BF16 ×2** | — | **待测** | ~13.6 GB | 唯一还未测的杠杆 |

**批处理**:❌ 模型硬性 `only batch size = 1`。**这推翻了早期「批处理带 4–8× 吞吐」的假设**——单卡吞吐 ≈ 单流吞吐(并发请求在一张卡上串行,几乎不叠加)。

**FP8 结论**:❌ 在当前 Blackwell(sm_120)软件栈上不通。版本矩阵死循环:torch 2.11 时 torchao 预编译 kernel 是给 Hopper(sm_90a)/py310 的、加载失败;降到 torch 2.8 后 torchao 又要 torch≥2.11、cpp 扩展被跳过。两种情况都退回没 kernel 的慢速软件 FP8,**比 BF16 还慢**。精度不受影响,但速度无收益。要真 FP8 须等 torchao/vLLM 的 Blackwell 支持成熟或用 TensorRT-LLM(工作量大且未必支持此自定义架构)。

**flash-attn 结论**:❌ 当前发行版装不上(见 §4.2)。收益本也有限(主要是原生分辨率不 OOM + 略快),而锁 768 已不 OOM、真瓶颈是无批处理它也救不了。

### 4.4 精度实测(关键——选型通过的决定性证据)

768 分辨率下,难点弹窗目标定位与本会话早前的**手工像素测量**对照:

| 目标 | 手工测量 | 模型定位(768) | 偏差 |
|---|---|---|---|
| IMG_0002 Shop 促销卡下方 × | (0.500, 0.785) | (0.501, 0.786) | **<0.2%** |
| IMG_0007 内嵌网页左上 × | (0.069, 0.755) | (0.070, 0.754) | **<0.2%** |
| IMG_0008 定位权限 Don't Allow | 底部按钮行 y≈0.81 | 行框 y 0.78–0.85 | **命中** |

**768 下全部 10 张目标定位准确。** 一句英文指令即可精准定位,等同人工标定,且 iPhone 8 一份先验通吃、无需逐机标定。

**分辨率精度地板**:512 下多数目标仍准,**但 shop 促销那个最小、最孤立的 ×(IMG_0002,仅 ~15px)会向上飘 ~2% 而 miss**。→ **生产锁 768 保精度**(或测 640 折中,尚未测)。

### 4.5 承载量测算(诚实修正)

公式:`单卡承载 ≈ GPU吞吐(张/秒) × 每台调用间隔(秒) × 0.6 余量`。

- **每台调用间隔**:「VLM 唯一指令源」+ 现实节奏(每步平均 ~5s 等待 + 视频停留随机 8–15s)→ 每台平均 VLM 调用间隔 **~7–8s**(盲滑切视频不占 VLM 调用,略延长)。
- **GPU 吞吐**:实测单流 BF16 768 = **2.1 张/s**(批处理/FP8 均不可用)。

| 用法 | 间隔 | 吞吐 | 单卡承载 |
|---|---|---|---|
| **VLM 唯一指令源(现实节奏)** | 7–8 s | 2.1 张/s | **~9–10 台** |
| 混合兜底(仅难点调 VLM) | 30 s | 2.1 张/s | ~38 台 |

**多实例(待测,预计 ×2 聚合 ~3.5–4 张/s)后**:VLM 唯一指令源 ~16–18 台、混合 ~68 台。BF16 显存限制下单卡最多 2 实例(FP8 不可用→塞不下第 3 份)。

**几百台 = 多卡分片。** 例:VLM 唯一指令源模式带 300 台约需 15–30 张卡(取决于多实例效果);混合模式约需 4–8 张卡。

## 5. 关键发现汇总

1. ✅ **模型选型通过**——精度达标,能力正对需求(文字指令定位坐标)。
2. ❌ **批处理不支持**——最大的吞吐杠杆没了,单卡≈单流。
3. ❌ **FP8 当前不通**——Blackwell 生态太新,torchao kernel 版本矩阵死循环。
4. ❌ **flash-attn 当前不通**——Ubuntu 25.10 太新,glibc 与 CUDA 12.8 冲突。
5. ⚠️ **承载量大幅下调**——「VLM 唯一指令源」单卡 ~10 台(裸),几百台=多卡。是早期把批处理当理所当然导致的乐观外推,已修正。
6. ✅ **精度地板 = 768**——512 会丢最小的 ×,生产锁 768。
7. ⚠️ **软件栈前沿性是主要摩擦源**——torch 2.11 / Ubuntu 25.10 / Blackwell sm_120 三者叠加,所有 kernel 级加速(flash-attn/FP8)都因「预编译产物不匹配」失败。这不是硬件/模型限制,是生态未跟上。
