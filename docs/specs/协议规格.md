# 协议规格(G0)

autotk 2.0 两条跨进程边界:**master ↔ perception**(新,GPU 感知)与 **master ↔ Hub**(复用现有管理中心)。总纲见 `../autotk-2.0-架构设计总纲.md` §6/§8。

---

## 1. master ↔ perception(GPU 感知服务,新)

Node 主控 ↔ Python GPU 服务。**HTTP**,图像走二进制(JPEG),服务端队列批处理。

### 1.1 设计约束(回溯公理)

- **每步一次组合查询**(承载量关键,总纲 §6):把「本页激活的 hazards + 本步 expected」的 phrase 一次性送去,而非每目标一次。
- **图像在 master 侧预处理**:下采样到 512/640(定生产分辨率后固定)+ JPEG 编码,省 WiFi 与 GPU 显存。
- **服务端批处理**:请求进队列,~10–30ms 窗口聚合多台成 batch(同分辨率无 padding),按 reqId 分发。
- **无状态**:每请求自带截图,服务端不存会话。

### 1.2 `POST /perceive` —— grounding 组合查询(唯一坐标源)

请求(`multipart/form-data` 或 `application/msgpack`):
```jsonc
{
  "reqId": "string",            // 幂等/回执关联
  "phoneId": "string",          // 仅日志/批调度分组
  "image": "<JPEG bytes>",      // 已下采样(长边 512/640)
  "imageW": 512, "imageH": 910, // 送入分辨率(用于把归一化框换回像素,可选)
  "queries": [                  // 组合:hazards + expected 的 phrase
    { "id": "sys.location-perm", "phrase": "the Don't Allow button", "region": [0.14,0.78,0.72,0.07] },
    { "id": "feed.like",         "phrase": "the like heart button on the right rail" }
  ]
}
```
响应:
```jsonc
{
  "reqId": "string",
  "boxes": [                    // 只返回「存在且置信」的目标;缺席目标不出现
    { "id": "feed.like", "bbox": [0.83,0.44,0.90,0.50], "score": 0.94 }
  ],
  "latencyMs": 61               // 服务端推理耗时(不含排队),供监控
}
```
- `bbox` 归一化 [x1,y1,x2,y2]∈[0,1];master 乘原始截图宽高得像素中心去 tap。
- **缺席即不返回**;`score < 阈值` 的也不返回(阈值可配,治 grounding 幻觉,总纲 §6 风险)。
- 危险目标命中后,若该 Target 带 `ocr`,master 可再发一次 `/ocr` 核字确认再动手(见 1.4)。

### 1.3 `POST /ocr` —— 文本读取(不参与坐标决策)

用于读评论内容 / 视频文案,喂 L3 业务逻辑(posPrompts/negPrompts/commentMatchKeywords 匹配)。
```jsonc
// 请求
{ "reqId": "s", "image": "<JPEG>", "region": [0.0,0.77,0.72,0.13] }  // region 可选,缺省全图
// 响应
{ "reqId": "s", "lines": [ { "text": "好看的视频 #beach", "bbox": [0.05,0.80,0.5,0.83] } ] }
```
引擎:PaddleOCR(GPU),或 CPU。中英文。

### 1.4 错误与降级

| 情况 | 行为 |
|---|---|
| 队列超时(>Xs) | 返回 `504`,master 按该 Step `onFail` 处理(通常重试) |
| 模型异常 | `500` + reason;master 记 health、告警 |
| 图像解码失败 | `400`;master 侧修预处理 |

### 1.5 批处理(服务端)

```
收到 /perceive → 入队(按送入分辨率分桶)→ 每桶攒到 maxBatch 或 windowMs 触发
→ 一次 model.generate(batch) → 按 reqId 拆分响应
```
`maxBatch`/`windowMs` 由 §性能报告 §8.2 批处理曲线定;同分辨率同桶,无 padding 损耗。

## 2. master ↔ Hub(管理中心,复用现有)

**复用 `services/hub` + `packages/shared` 现有 socket.io 协议**(`shared/src/protocol.ts` 的 `EVT` + 消息体),不另造。变化仅在**连接主体**:旧模型「每台手机一个 socket」→ 新模型「master 代理 N 台」。

### 2.1 现有协议已覆盖的(直接复用)

- **状态/日志**:`DeviceStatus`(running/module/page/stats/alert/battery)、`DeviceLogMsg`。
- **批量配置**:`ConfigPatch`——**已含本项目全部业务参数**,含 `following`(关注监控/打粉)、`kwSearchExecRatio`、`clickWaitTime`、`allDay`、`taskWindows`、各模块 `ModuleParamsPatch`。master 收 `config:apply` 分发到对应 PhoneSession。
- **发布**:`PublishTask` 状态机(scheduled→…→published)。master 收 `publish:task` 驱动 publish 工作流。
- **看板运维**:改名/删除/日志订阅等。

> ⭐ `ConfigPatch` 就是 L3 业务参数的下发面——L3 业务规格的字段与它对齐(两端共用,防漂移,是既有跨项目纪律)。

### 2.2 唯一需决策的:master 如何代理 N 台(D3)

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 平铺(推荐起步)** | master 为每台手机开一个逻辑 device 身份,复用**现有协议逐字节不变**(每台照常 `device:register`/`device:status`/…,deviceId=手机 udid) | 零协议改动、Hub 无感;代价 = 一个 master 进程维护 N 个 socket 连接(几百个连接需压测) |
| **B. 聚合方/子设备** | master 作单一 aggregator 连接,给每类 per-device 消息加 `deviceId` 维度(需扩 `DeviceStatus`/`DeviceLogBatch` 带 deviceId + 新 handshake role `aggregator`) | 连接数少、扩展性好;代价 = 扩 `shared` 协议 + 改 Hub gateway |

**建议**:G5 起步用 **A**(零改动、快落地、复用久经考验的 Hub);连接数成瓶颈再升级到 **B**。协议扩展点预留在 `shared`。

> ✅ **已拍板(2026-07-20):方案 A**——见 `docs/决策记录-2026-07-20.md` D3。

### 2.3 遥测(复用)

`@telemetry/sdk` → `services/telemetry-collector`。master 侧初始化 `initTelemetry()`(env `TELEMETRY_URL`,未设 no-op),每台手机作一个匿名维度。静默卖家遥测,无买家看板(既定 P4 方案)。

## 3. 端到端数据流(一步)

```
主控循环(master, 每台每步):
  1. WdaClient.screenshot(phone)                    → PNG Buffer
  2. 预处理:下采样长边→512 + JPEG                    (master, 省带宽/显存)
  3. POST /perceive { image, queries:[hazards∪expected] }  → boxes   (perception, 批处理)
  4. decide():危险优先→期望→轮询(总纲 §5)           (master, 纯逻辑)
  5. WdaClient.tap/swipe/typeText(phone)             → 执行
  6. 需读文本时 POST /ocr                            (评论/文案 → L3 匹配)
  7. 汇总到 PhoneSession;定期 device:status/log → Hub  (聚合上报)
```

## 4. G0 交付边界

本规格定义**接口形状与语义**,不含实现。落地:`/perceive`·`/ocr` 在 G2(感知服务),Hub 对接在 G5。协议扩展(方案 B)若采用,`shared` 改动登记进跨项目同步纪律。
