## 逐条细节与生效动作

### D1 · 承载模式 = 纯 VLM 唯一指令源
- 决定:按「VLM 是坐标/决策唯一来源」实现(维持架构原则);混合兜底模式不做。
- VLM 侧优化(多实例、FP8、flash-attn、更快推理栈)**后续尽量做**,但不进 MVP 关键路径(与 D7 合并语义)。
- 含义:近期承载按**单卡 ~10 台(裸 BF16)**规划;几百台 = 多卡分片。报价/采购不得按未实测的优化数字承诺。

### D2 · 手机 IP = DHCP 静态租约 + 配置表
- 做法:每台手机在路由器上做 **DHCP 静态租约**(MAC→固定 IP);master 侧维护**设备配置表**(UDID / IP / 编号 / 机型尺寸),装机台注册 UDID 时顺手登记;master 启动对表内 IP:8100 **探活校验**,失败即报警;全网段扫描只作人工诊断工具。
- 影响范围(拍板时需求方问及):
  1. **装机流程**——每台新手机多一步「路由器绑租约 + 登记配置表」;
  2. **`services/master` 配置文件形状**——devices 列表是装配 N 个 WdaClient 的输入(下一编码任务的接口);
  3. **故障诊断**——IP 漂移=探活失败即时报警,而非静默连错手机。
- **不影响** `@auto/core`:Fleet 收现成 driver 实例,IP 只存在于 master 装配层。

### D3 · Hub 对接 = 方案 A 平铺
- master 为每台手机开一个逻辑 device 身份(deviceId=UDID),现有 socket.io 协议**逐字节不变**,Hub/desktop 无感。
- 几百连接需压测;若成瓶颈再升方案 B(聚合方/子设备),协议扩展点已在 `@mc/shared` 预留,不返工。
- `docs/specs/协议规格.md` §2.2 已标注拍板结果。

### D4 · License = MVP 不接
- MVP 阶段 master **不接激活门禁、不发心跳**;`services/license` 服务本身不动(独立产品线继续)。
- 授权粒度(按手机/按主机/按槽位)顺延至商用化阶段再拍;届时需查 license 后端「一 key 多设备上限」现状能力。

### D5 · 生产 GPU 主机 OS = Ubuntu 24.04 LTS
- 依据:25.10 的 glibc 2.41/g++15 与 CUDA 12.8 冲突导致 flash-attn 不可编译、FP8 kernel 矩阵死循环——24.04 是未来启用这些优化的唯一留路。
- 现有 Windows GPU 机继续 WSL 开发不受影响;仅约束生产采购装机。

### D6 · 生产分辨率 = 640(不再专门 bench)
- 决定:perception 服务默认 `--max-side 640`(**本仓库已改**:`services/perception/server.py`)。
- **已知风险(拍板时已知悉)**:精度实测只覆盖 768(十张全准)与 512(丢 ~15px 的 shop 促销 ×);640 未实测。
- 安全网:真机联调第 2 步「逐目标验注册表关键目标」本来就要做——在 640 下做即等于补上这轮实测,**若小目标定位不稳,回退 768 只是改一个启动参数**。

### D7 · 吞吐优化 = 全部搁置
- 多实例 ×2、FP8、flash-attn、TensorRT-LLM 一律不投入,**先全流程跑通**(冒烟→逐目标→组合指令→私信→单工作流→多机)。
- 后续在 24.04 生产机上按 D1 的「尽量优化」原则复测;FP8 若将来启用,**必须先真机复核坐标精度不塌**(既有纪律)。

### D8 · 旧 apps/mobile = 彻底退役

  - `services/update-server`(expo-updates 热更)暂无服务对象,去留后续处置。

### P1 · 组合多目标指令预案 → **⚠️ 已被真机证伪并取代(2026-07-21)**
- **真机实测结论(2026-07-21)**:LocateAnything-3B 是**单目标 grounding 模型**——一次组合查询(编号列 2/3/4/5/6 个目标)**即使格式服从也只返回第一个目标**(smoke `TARGETS=a,b,c` 逐数验证:命中数恒为 1)。这与模型架构一致(PBD 框头 + 自定义 `generate(generation_mode="hybrid")`,原生任务即单指代表达;bench.py `ground()`、server.py 全走单 phrase)。
- **因此「组合查询 + P1 退化」整套设计作废**,由**单目标逐查**取代:`perceptor-vlm/src/perceptor.ts` 的 `locate()` 改为对每个 query 各发一次 `buildFindInstruction` 单目标指令(同一帧图),命中按序回填、各过 region 过滤。`buildLocateInstruction`/`parseLocateResponse`/`locateResponseComplies`(组合协议)+ P1 退化分支**已删除**(2026-07-21)。
- **引擎侧同步**:`automation-core/src/engine.ts` 的 `observeStep` 改逐个单查——**危险优先**仍是公理。
- 原「取第一个」的本意(需求方 P1 指示)在单目标模型下自然满足:根本不存在"多目标同时返回"。temperature:见 P2 合并说明。

#### P1′ · 危险检测「一次 OCR 读屏」——为多机吞吐(2026-07-21,需求方要求"速度一定要保证")
- **问题**:逐个 grounding 查危险,单目标模型下 N 危险 = N 次定位;且模型对不存在目标幻觉出框(真机日志:该页 7 个危险 7 个全幻觉),每个还触发一次 OCR 框内复核 → **每轮 ≈ 15 次 VLM ≈ 7 秒**,几百台跑不动。
- **需求方拍板**:危险优先**不动**,把"逐个查危险"收成**一次检测**("把危险检测的目标放到一次检测里")。
- **落地**:`detectHazard` 每轮**读一次屏上文字**(`perceptor.readText` 全屏),用各危险的 `ocr` 特征在文本里匹配——命中即在场(靠真实文字,天然过滤 grounding 幻觉),只对命中的那个再定位关闭键(点按类 deny/allow/tapBox;手势类 swipeAway/back/skip 连定位都免)。**干净页 = 1 次 OCR;有弹窗 = 1 OCR + 1 定位**(从 ~15 次降到 ~2 次,单卡承载翻 ~7 倍)。危险优先、全部危险覆盖均不变。
- **约束**:凡进 `activation.pageHazards`/`globalHazards` 的危险都**必须带 `ocr`**(否则一次检测测不到 → 退回 grounding 兜底)。**内容类标记(`feed.live-tag`/`feed.ad-marker`/`comment.ad-first`)移出页级危险**——全屏 OCR 下 "LIVE"/"广告"字幕会误伤;它们本是内容过滤,已由 `following.ts`/`search.ts`/`comments.ts`(`c.isAd`)显式判。
- 测试:engine +4(OCR 优先专项,含"多危险共用一次读屏"断言)= core 77;plugin +1 = 85。真机需验:OCR 读屏延迟、特征词精度(短词如 not now/cancel 防字幕假阳)。

### P2 · grounding 幻觉预案
- 需求方指示:temperature 调高一些 + 按原建议做(置信度阈值/二次确认)。
- **现状澄清**:perception 服务与 bench 一直是 `temperature=0.7, do_sample=True, top_p=0.9`(官方示例参数),**全部精度实测数据都在 0.7 下测得**;请求体里的 `temperature` 字段原先被服务端忽略。
- 落地(**本仓库已改** `server.py`):`--temperature` 成为启动参数,**默认 0.8**(按「稍调高」);请求体 `temperature` 字段现已生效(可覆盖默认)。
- **技术注记(工程侧保留意见,已在拍板沟通中说明)**:更高温度=输出更随机,与「减少幻觉」方向相反的风险存在。故做成可配:真机逐目标验收时对比 0.7 vs 0.8,若框抖动/幻觉率上升即回调——决策权在需求方。
- 危险目标「疑似命中二次确认」按原建议保留为验收不达标时的升级手段。

### P3 · 私信 = 必做 + 失败记录
- 功能③(私信评论者)保留为 MVP 必做项。
- **失败必须记录**:现状 `plugin-tiktok/src/workflows/dm.ts` 只有「无私信按钮 → 记 `dm-tried`」;打开私信失败/输入失败两条路径**没有持久记录**,且输入失败仍返回 "sent" 并占每日配额——需改(任务 T4)。

### D9 · 发布视频投递 = 极小「收视频 App」(2026-07-20 追加拍板)
- **背景/为什么绕不开**:2.0 手机零决策代码,养号/搜索/评论/私信/打粉 + 发布的 **UI 操作**全由 WDA+VLM 完成(`publish.ts` 已写好 `+→上传→选相册最新→…→发布`)。但 TikTok 发布前提是**视频文件已在相册**,而 **iOS 从根上不允许非 App 写入相册**(WDA 只能点 UI 不能注入文件;AFC/USB 注入相册在现代 iOS 已封)。旧系统靠 `apps/mobile` 的 RN App 下载+存相册,已被 D8 退役砍掉 → **出现执行者真空**(`publish.ts` 头注释「视频已由 Hub 存入相册」是空头支票)。
- **拍板:每台装一个极小「收视频 App」**——哑文件槽,**只干「下载视频→存相册」**,无 OCR/无定位/无决策(决策仍 100% 在 master)。故**不违背 D8**(D8 砍的是引擎的脆弱性,不是文件槽)。
- **可抢救的旧资产**:`apps/mobile/src/publish/downloader.ts` + `album.ts`(下载+存相册,~100 行)+ `services/publisher/src/lan-server.ts`(LAN token 发文件)+ `services/publisher` 文件夹工作流/文案。
- **投递链路(目标形态)**:管理中心桌面(文件夹工作流,复用)扫视频+文案 → Hub `publish:task`(D3 平铺发到 master)→ **master 触发该机收视频 App 从 LAN 拉视频→存相册**(App 经 WDA `activateApp` 唤起或轮询)→ 存好后 master 切回 TikTok 走 `publish.ts` 发布 → 回报。
- **⚠️ 只能 Mac/真机构建验证**:收视频 App 是 iOS App(RN+原生 expo-media-library 或原生 Swift),本机(Windows,无 Mac)**无法构建**;装机台已在分发 IPA 母包,多分发一个即可。列为 Mac-build 任务(见任务 T7/T8)。
