## 逐条细节与生效动作

### D1 · 承载模式 = 纯 VLM 唯一指令源
- 决定:按「VLM 是坐标/决策唯一来源」实现(维持架构原则);混合兜底模式不做。
- VLM 侧优化(多实例、FP8、flash-attn、更快推理栈)**后续尽量做**,但不进 MVP 关键路径(与 D7 合并语义)。
- 含义:近期承载按**单卡 ~10 台(裸 BF16)**规划;几百台 = 多卡分片。报价/采购不得按未实测的优化数字承诺。

### D2 · 手机 IP = DHCP 静态租约 + 配置表
- 做法:每台手机在路由器上做 **DHCP 静态租约**(MAC→固定 IP);master 侧维护**设备配置表**(UDID / IP / 编号 / 机型尺寸),装机台注册 UDID 时顺手登记;master 启动对表内 IP:8100 **探活校验**,失败即报警;全网段扫描只作人工诊断工具。
- 影响范围(拍板时需求方问及):
  1. **装机流程**——每台新手机多一步「路由器绑租约 + 登记配置表」;
  2. **`services/master` 配置文件形状**——devices 列表是装配 N 个 WdaClient 的输入(下一编码任务的接口);
  3. **故障诊断**——IP 漂移=探活失败即时报警,而非静默连错手机。
- **不影响** `@auto/core`:Fleet 收现成 driver 实例,IP 只存在于 master 装配层。

### D3 · Hub 对接 = 方案 A 平铺
- master 为每台手机开一个逻辑 device 身份(deviceId=UDID),现有 socket.io 协议**逐字节不变**,Hub/desktop 无感。
- 几百连接需压测;若成瓶颈再升方案 B(聚合方/子设备),协议扩展点已在 `@mc/shared` 预留,不返工。
- `docs/specs/协议规格.md` §2.2 已标注拍板结果。

### D4 · License = MVP 不接
- MVP 阶段 master **不接激活门禁、不发心跳**;`services/license` 服务本身不动(独立产品线继续)。
- 授权粒度(按手机/按主机/按槽位)顺延至商用化阶段再拍;届时需查 license 后端「一 key 多设备上限」现状能力。

### D5 · 生产 GPU 主机 OS = Ubuntu 24.04 LTS
- 依据:25.10 的 glibc 2.41/g++15 与 CUDA 12.8 冲突导致 flash-attn 不可编译、FP8 kernel 矩阵死循环——24.04 是未来启用这些优化的唯一留路。
- 现有 Windows GPU 机继续 WSL 开发不受影响;仅约束生产采购装机。

### D6 · 生产分辨率 = 640(不再专门 bench)
- 决定:perception 服务默认 `--max-side 640`(**本仓库已改**:`services/perception/server.py`)。
- **已知风险(拍板时已知悉)**:精度实测只覆盖 768(十张全准)与 512(丢 ~15px 的 shop 促销 ×);640 未实测。
- 安全网:真机联调第 2 步「逐目标验注册表关键目标」本来就要做——在 640 下做即等于补上这轮实测,**若小目标定位不稳,回退 768 只是改一个启动参数**。

### D7 · 吞吐优化 = 全部搁置
- 多实例 ×2、FP8、flash-attn、TensorRT-LLM 一律不投入,**先全流程跑通**(冒烟→逐目标→组合指令→私信→单工作流→多机)。
- 后续在 24.04 生产机上按 D1 的「尽量优化」原则复测;FP8 若将来启用,**必须先真机复核坐标精度不塌**(既有纪律)。

### D8 · 旧 apps/mobile = 彻底退役
- 理由(需求方):纯 OCR/像素启发式方案太脆弱。
- 含义:
  - 不再投入任何开发/维护(含 OTA 热修);**新框架是唯一主线**。
  - 原「双轨并跑至影子对比达标后切换」的过渡策略作废——不存在双轨了。
  - phase 4「把 apps/mobile 收编进 root workspace」计划作废;CLAUDE.md 耦合缝表中所有 mobile 相关同步纪律**冻结**(telemetry SDK 只剩 desktop/license 两份副本需同步)。
  - `services/update-server`(expo-updates 热更)暂无服务对象,去留后续处置。
  - 代码暂留仓库作知识库(WDA×TikTok 教训已提炼进 `docs/specs/`);何时物理删除另行安排。

### P1 · 组合多目标指令预案
- 需求方指示:temperature 稍微调高;**如果有多目标,只固定取第一个**,实现处加注释标记。
- 实现解释(两层,已按此理解落地/立项;若与本意不符,改这里):
  1. **同一目标返回多框** → 取第一个合法框:`perceptor-vlm/src/protocol.ts` 的 `parseFirstBox` / `parseLocateResponse`(seen 去重)**现状即是此行为**,无需改。
  2. **组合响应整体不可解析**(模型不服从多目标格式)→ 退化为「只查优先级最高的第一个目标」发单目标指令(`buildFindInstruction`),**代码处加注释标记**——待实现(任务 T3),且真机先测组合服从度,不服从才启用退化路径。
- 温度:见 P2 合并说明。

### P2 · grounding 幻觉预案
- 需求方指示:temperature 调高一些 + 按原建议做(置信度阈值/二次确认)。
- **现状澄清**:perception 服务与 bench 一直是 `temperature=0.7, do_sample=True, top_p=0.9`(官方示例参数),**全部精度实测数据都在 0.7 下测得**;请求体里的 `temperature` 字段原先被服务端忽略。
- 落地(**本仓库已改** `server.py`):`--temperature` 成为启动参数,**默认 0.8**(按「稍调高」);请求体 `temperature` 字段现已生效(可覆盖默认)。
- **技术注记(工程侧保留意见,已在拍板沟通中说明)**:更高温度=输出更随机,与「减少幻觉」方向相反的风险存在。故做成可配:真机逐目标验收时对比 0.7 vs 0.8,若框抖动/幻觉率上升即回调——决策权在需求方。
- 危险目标「疑似命中二次确认」按原建议保留为验收不达标时的升级手段。

### P3 · 私信 = 必做 + 失败记录
- 功能③(私信评论者)保留为 MVP 必做项。
- **失败必须记录**:现状 `plugin-tiktok/src/workflows/dm.ts` 只有「无私信按钮 → 记 `dm-tried`」;打开私信失败/输入失败两条路径**没有持久记录**,且输入失败仍返回 "sent" 并占每日配额——需改(任务 T4)。
