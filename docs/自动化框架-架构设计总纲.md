# 自动化框架架构总纲

> 状态：当前实现说明，2026-07-23。
> 部署与测试入口：[`真机部署手册.md`](真机部署手册.md)。
> 业务/WDA/协议细节：[`specs/`](specs/)。

## 1. 目标与边界

autotk 2.0 是一个集中式 iOS 屏幕自动化系统：

- 手机只运行 WDA 与目标 App；
- 截图、识别、决策、调度在主控侧；
- LocateAnything-3B 是坐标来源；
- OCR 只负责读取文字和页级危险预筛；
- core 与具体 App 解耦，TikTok 能力放在插件；
- 每个改变页面的动作必须由下一帧验证；
- 无法确认时停手并告警，不盲目脱困。

当前首个插件是 TikTok，交付范围：

1. 搜索互动 `search`
2. 主页互动 + 私信 `profileAndDM`
3. 关注监控 `followMonitor`
4. 发布 `publish`
5. 评论区滚动与互动（被多个工作流复用）

旧 `apps/mobile` 的手机端引擎、坐标标定、OCR/像素识别与 License/OTA 链路已退役，不是 2.0 运行时的一部分。

## 2. 第一性约束

- **屏幕是唯一真相**：TikTok 元素树不可依赖，业务只看截图。
- **动作没有业务成功返回值**：tap/swipe 只表示请求已发送，结果必须重新观察。
- **环境非确定**：网络、弹窗、广告、权限窗和 TikTok 变版随时改变页面。
- **识别是稀缺资源**：VLM 调用是吞吐瓶颈，不能假设批处理或免费并发。
- **危险优先**：遮挡当前页面的危险必须先处理，再执行期望动作。
- **停止优先于误触**：升级链终点是 `alertOperator`。
- **依赖倒置**：core 定义端口，driver/perceptor/plugin/state 实现端口。

## 4. 包与依赖方向

```text
@auto/core
  ↑            ↑                 ↑
driver-ios-wda perceptor-vlm     plugin-tiktok
  \             |                /
   \            |               /
            services/master
                  |
              @mc/shared
                  |
             services/hub
                  |
              apps/desktop
```

### 4.1 `@auto/core`

只定义跨 App 的机制：

- `Driver`
- `Perceptor`
- `StateStore`
- `Target`
- `Step`
- `RunContext`
- 决策引擎
- Fleet/PhoneHandle 编排
- 调度、暂停、独占运行、看门狗、退避与熔断

core 不导入 TikTok 插件。

### 4.2 `@auto/driver-ios-wda`

实现：

- 建立与恢复 WDA session；
- `snapshotMaxDepth=1` 等快速设置；
- screenshot；
- W3C `/actions` 点按/滑动；
- `/wda/keys` 输入；
- App 前台切换；
- 请求超时与会话自愈。

### 4.3 `@auto/perceptor-vlm`

实现 OpenAI 兼容多模态客户端：

- 发送 PNG data URI；
- grounding 定位；
- OCR 读文本；
- 超时与 HTTP 错误；
- region 后过滤；
- LocateAnything 单目标逐查。

### 4.4 `@auto/plugin-tiktok`

持有所有 TikTok 语义：

- Target 注册表；
- 页面危险激活规则；
- 业务参数与校验；
- 三个常驻工作流；
- 发布工作流；
- 评论、私信、恢复等动作；
- `pickWorkflow` 优先级。

### 4.5 `services/master`

负责运行时装配：

- 读取/校验设备配置；
- 自动发现 WDA；
- 为每台手机创建 driver；
- 共用 perceptor 与 state；
- 建立 Fleet；
- 连接 Hub；
- 接收配置/启停/发布任务；
- 管理 receiver；
- 上报状态；
- 输出运行日志；
- 提供 smoke 与一次性 workflow runner。

## 5. 核心端口

```ts
interface Driver {
  screenshot(): Promise<Uint8Array>;
  windowSize(): Promise<{ width: number; height: number }>;
  ensureHealthy(): Promise<void>;
  tap(point: { x: number; y: number }): Promise<void>;
  swipe(from: Point, to: Point, durationMs: number): Promise<void>;
  typeText(text: string): Promise<void>;
  activateApp(bundleId: string): Promise<void>;
}

interface Perceptor {
  locate(image: Uint8Array, queries: LocateQuery[]): Promise<Hit[]>;
  readText(image: Uint8Array, region?: Box): Promise<TextLine[]>;
}

interface Plugin {
  id: string;
  appId: string;
  targets: Target[];
  activation: Activation;
  workflows: Record<string, (ctx: RunContext) => Promise<void>>;
  defaultParams: unknown;
  validateParams(params: unknown): void;
}
```

`StateStore` 当前生产装配仍使用内存实现。Postgres 实现是上线前缺口，因为私信去重与每日限量需要跨重启持久化。

## 6. 四层操作模型

```text
L3 工作流  plugin   search/profileAndDM/followMonitor/publish
L2 动作    plugin   评论互动/私信/视频互动/恢复
L1 闭环    core     runStep/locate/tapTarget/readText/await
L0 原子    driver   screenshot/tap/swipe/typeText/activateApp
```

L0 不理解 TikTok；L1 不理解某个具体页面；L2/L3 才具有 App 语义。

## 7. Step 闭环

一个 Step 声明：

```ts
interface Step {
  intent: string;
  act?: BasicOp;
  expected: string[];
  hazards: string[];
  verify: string[];
  timeout: number;
  onFail: Escalation[];
}
```

执行顺序：

1. 截图；
2. 检测页级危险；
3. 有危险则按安全 handler 处理并重新观察；
4. 定位本步 expected；
5. 仅在 expected 成立时执行 act；
6. 轮询 verify；
7. 超时后按 retry → variants → recover → alertOperator 升级；
8. 最终无法确认时停止，不继续猜页面。

固定 sleep 只用于拟人停留，不用于等待页面加载；页面加载使用可观察的 verify 轮询。

## 8. 当前感知事实

### 8.1 单目标 grounding

LocateAnything-3B 已被真机证实为单目标模型：

- 一次组合提示只可靠返回第一个目标；
- `Perceptor.locate()` 对每个 query 各发一次推理；
- 同一组查询复用调用方提供的同一张截图；
- 不存在组合查询退化协议；
- 不支持 batch > 1。

任何仍写“每步一次组合查询 / 服务端批处理”的旧说明都已失效。

### 8.2 危险检测

页级危险不是逐个 grounding：

1. 每轮先对全屏做一次 OCR；
2. 用激活危险的 `ocr` 特征匹配文字；
3. 命中才定位对应安全按钮；
4. 点按后重新观察。

这样干净页面是一次 OCR，有弹窗通常是一次 OCR + 一次定位。

约束：

- 页级危险应有明确 `ocr` 特征；
- 无 `ocr` 的危险才退回逐个定位；
- `feed.live-tag`、`feed.ad-marker`、`comment.ad-first` 等内容分类不进入页级危险；
- 内容分类由工作流显式定位并决定“跳过/不互动”。

### 8.3 分辨率与温度

- 生产默认 `max-side=640`；
- 768 已有更完整精度样本；
- 512 会漏小关闭按钮；
- 640 必须随真机逐目标验收；
- 小目标不稳回 768；
- 当前服务基线温度 0.7；
- 不启用 FP8/flash-attn。

## 9. 调度与工作流选择

每台 PhoneHandle 的主循环：

1. 检查暂停；
2. 检查运行时段；
3. 等待发布等独占任务；
4. `pickWorkflow`；
5. 运行前 `recoverToFeed`；
6. 执行目标工作流；
7. 统计与状态上报；
8. 失败退避，连续失败熔断。

工作流选择：

- `activeWorkflow` 显式值优先；
- `off` 表示 idle；
- `followMonitor` 需要 `following.moduleEnable=true`；
- `profileAndDM` 需要 `persHome.moduleEnable=true` 且每天至多一次；
- `search` 需要非空 `searchKeywords`；
- 未显式选择时保留旧 moduleEnable 优先级兼容。

发布不在无参工作流映射中，由 Hub 发布任务带 `caption/source` 触发，并通过 `runExclusive` 与养号工作流串行。

## 10. Hub 与 desktop

当前采用 D3 平铺方案：

- master 为每台手机建立一个 device socket；
- deviceId 来自 master 配置/自动发现身份；
- Hub 协议复用 `@mc/shared`；
- desktop 可选择工作流、批量配置、暂停/恢复；
- desktop 自动启动 bundled master；
- desktop 显示后台识别与发现状态并支持重启；
- 发布任务从 desktop → Hub → master。

状态上报已经接通。日志排障的稳定来源是 desktop 当日文件日志与一次性 runner 产物；Hub/desktop 的实时日志缓冲属于运行时便利功能，不是持久审计库。

## 11. 发布链路

```text
desktop 文件夹
→ 局域网 URL
→ Hub publish task
→ master publish orchestrator
→ receiver 下载并存相册
→ PhoneHandle.runExclusive
→ TikTok publish UI
→ publish result
→ desktop 去重登记
```

receiver 是“哑文件槽”，不做视觉识别和业务决策。

当前阻塞：

- master URL 与 deviceId 仍以 `EXPO_PUBLIC_*` 构建期写入；
- 同一 receiver IPA 暂不能直接量产给 N 台；
- 自动发现身份与真实 UDID 未统一；
- Mac/真机后台保活、权限、入相册尚需验收。

## 12. 测试分层

| 层 | 验证什么 | 不验证什么 |
|---|---|---|
| 纯逻辑 Vitest | 决策、协议、参数、工作流分支、编排 | 真设备/模型/UI |
| smoke | WDA 截图 → VLM 定位 → 可选点击 | 完整工作流 |
| 一次性 workflow runner | 一台/一个工作流、生产接线、结构化留证 | 常驻调度/多机 |
| desktop 真机 | Hub、远程配置/启停、自动发现 | 大规模承载 |
| 多机/长稳 | 错峰、Wi-Fi、WDA、GPU | 未测机型/新 TikTok 版本 |

自动化全绿不能替代真机验收。当前状态与剩余项见 [`项目进度报告.md`](项目进度报告.md)。
